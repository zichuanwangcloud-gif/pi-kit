# Idea to Spec 设计说明

`linear-to-pr` 假设已经有一个写清楚的 Issue；需求缺口达到 3 个就停止。但日常最常见的输入恰恰是一句话、
一个模糊场景或一段聊天记录——既不知道要做什么，也不知道边界，更定不下验收标准。`idea-to-spec` 补的就是
「一句话 → 可开工需求」这一段。

## 核心判断：验收标准是收敛出来的

需求模糊时，验收标准无法靠「判断」得出。提需求的人很少能说清自己要什么，但几乎总能对一个具体例子
说「对」或「不是这样」。所以 Skill 的主循环不是问答，而是**出例子 → 让人挑和否决 → 重写例子**。
每一轮最多 3 个问题、3–5 个例子，其中故意放边界和反例，让分歧尽早暴露。

## 为什么先分离问题与方案

一句话需求通常是方案（「加个导出按钮」）。直接为方案写 AC，可能做出完全符合描述、却没解决问题的东西。
Skill 先产出一句不含方案的问题陈述（谁 / 场景 / 现状 / 损失 / 绕行），字面方案只作为候选。

## 为什么要做代码取证

很多模糊需求查一下现状就清楚了：功能其实已存在但入口太深、问题其实出在权限配置。AI 在这一步最有优势，
而且取证可能直接改写问题本身，所以放在提问之前。

## 边界靠「范围外」画出来

例子的「不要」和「以后」都显式写进范围外。再做一次反向推演——「AC 全过后原问题还会在什么情况下出现」——
把答案补成 AC 或写进范围外。没写出来的边界等于没有边界。

## 问不出来的未知转成探查

有些未知只有试了才知道（用户会不会用、第三方接口有多慢）。此时硬写功能 AC 是在伪造确定性。
Skill 改产出探查型 spec：验收的是「问题被回答」，带时间盒和「结论 → 下一步」映射。

## 需求方不在场

和 Skill 对话的常常是开发者，不是提需求的人。业务取舍不由开发者或 AI 拍板，而是放进一份可直接转发的
「需求方确认清单」；清单清空之前 spec 状态只能是 `待需求方确认`。

## 为什么产物是 Markdown、不写 Issue 系统

需求收敛不该绑定某个 tracker。产物是可移植的 Markdown，段落与 `linear-to-pr` 的理解卡一一对应、
八项自检口径相同：粘贴进 Linear Issue 后即可交给 `linear-to-pr`，也可以直接作为任何开发流程的输入。
Skill 唯一的写操作是新建这份文档，因此不需要任何 API key，也不会产生外部副作用。
