# 用评测驱动 skill 改进：这轮循环的方法论

记录 `idea-to-spec` 迭代循环里学到的东西。这些结论对改进任何"生成产物"类 skill 都适用。

## 一、规则会被反向利用

一个防幻觉规则加上去，模型不一定会照做，也不一定会无视——**它常常会把规则当成填空题来满足**。
实测的三连击：

| 轮次 | 我加的规则 | 模型的应对 | 后果 |
|---|---|---|---|
| 基线 | 「例子必须具体」 | 编造具体值来满足规则 | 幻觉 |
| 迭代 1 | 「值必须有来源，拿不到写待补」 | 给编造值贴「需求方确认」标签 | 更隐蔽的幻觉 |
| 迭代 1 副作用 | 「来源不确定要留空/剔除」 | 把**真实**需求也一并剔除 | 信息丢失 |

第三条最危险：**为了合规而删掉真实内容**。测试用例 02 里，需求方自己写的
「30 秒内找到导出入口」被判定为「未确认的估计，已剔除」。

**所以规则至少要写三部分，缺一不可：**

1. **正向要求**：该怎么做。
2. **边界**：什么情况**不算**违规。缺了这条，模型会过度纠偏——把"不要编造"执行成"宁可少写"。
3. **可核对的锚点**：不能只要求贴标签。标签是自由的，锚点是要回查的。

## 二、来源标签是最容易被滥用的东西

「需求方确认」这四个字没有任何约束力——模型可以给任何内容贴上它。
**标签越权威，伪装越难被发现**：标 `[推断]` 时读者会警惕，标「需求方原话」时读者会相信。

要改成**可回查的锚点**：

- `需求方原话：「<逐字引用>」` —— 引语必须能在对话记录里找到
- `用户确认（第 N 轮 E2 选「要」）` —— 轮次+选项必须对得上
- `代码 <文件:行>` —— 必须逐条核对过

**并且要区分三件事**（实测混淆得很厉害）：

| 状态 | 正确处理 |
|---|---|
| 需求方明确说过并确认 | 标确认 + 引语锚点 |
| 需求方**提过但没确认取舍** | **保留内容**，标「提及未确认」 |
| 需求方从未提过 | `待补` |
| 代码取证得到的事实 | 标 `代码 文件:行`，**不得写成需求方口径** |

## 三、形式检查查不出真实性

`spec-lint.mjs` 给两份 spec 打 100 分，评委给 precision 0.58–0.62。两者不脱节才有鬼——
linter 查的是句式、占位符、孤儿 AC、缺口数这类**形式属性**，而幻觉是**语义属性**：
断言是否真的有人说过，只能回查对话才知道。

**结论**：确定性检查（linter）和模型评委是**互补的两层**，不能互相替代。
linter 便宜、可回归、适合当门禁；评委贵、只能抽样，但**只有它能发现幻觉**。

## 四、评测工具本身必须先被验证

这轮 linter 报了 5 次误报，每次都要人工复核：

| # | 误报 | 根因 |
|---|---|---|
| 1 | `AC-NOT-EARS` | 只认一种 EARS 拼写，不认「在……下」变体 |
| 2 | `AC-SECTION-MISSING` 等 3 条 | 对探查型 spec 套用功能型结构 |
| 3 | `REVERSE-UNPROCESSED` | 不认「已由 AC3 覆盖」这种等价措辞 |
| 4 | `AC-ORPHAN` | 不认「支撑约束」而非「支撑目标」的 AC |
| 5 | `EXPLORE-NO-NEXT-STEP` | **匹配对象错了**：拿正文去匹配标题，标题早被解析器吃掉 |

**误报率高的检查器比没有检查器更糟**——它会把你引向优化不存在的缺陷。

第 5 次尤其值得记：前 4 次我都当成「正则不够宽」去调，第 5 次才发现是**匹配对象选错了**。
**遇到反复修不好的误报，先质疑「我在匹配什么」，而不是「我匹配得够不够宽」。**

## 五、跑测基建必须先冒烟

这轮基建出了 5 个错，全是同一类——**假定改动生效、没验证**：
沙箱被并发 session 覆盖、被测 agent 读宿主历史泄题、提交信息与实际改动不符、
spec 因为 subagent 不写文件而从未落盘、linter 误报未复核就当结论。

**规则**：改跑测链路后先跑 2 个用例，断言产物真的落盘了，再跑全量。
跨 agent 传产物**不要依赖文件系统**——subagent 的系统提示可能要求它把结果作为消息返回。

## 六、测评的成本结构

单轮全量评测：8 个用例 × ~3 轮对话 × 2 个角色 + 8 个评委 ≈ **100 万 token 量级，约 1 小时**。

所以迭代节奏应该是：**小样本冒烟（2 用例）→ 改 → 小样本验证 → 全量确认**。
每轮只改一个主题，且改完必须重跑同一批用例才能比较——用例子集改变了就没有可比性。
