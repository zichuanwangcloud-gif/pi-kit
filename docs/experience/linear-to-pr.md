# Linear → PR 使用经验

## Issue 形态先于需求内容

读到正文就开工是最常见的返工来源。开始审阅评论之前先看 Issue 的形态与状态，命中任一条即停止询问：

| 情况 | 为什么必须先停 |
|---|---|
| 已取消 / 已完成 | 需求可能已作废或已实现，按正文实现等于重复或回退 |
| `relations` 含 duplicate | 真实口径在 canonical issue 上，正文常是过期副本 |
| 含子 issue 的 parent | parent 正文是范围汇总，不是任一子任务的实现口径 |
| 被未完成的前置 issue 阻塞 | 需要先决定栈式 PR 还是等待，不能默认从长期分支起步 |

`parent` 非空但自身无子 issue 时不停止：读 parent 正文作为上下文，理解卡里标注来源为父 Issue，但不把兄弟 issue 的范围算进来。

## 需求来源不只有正文

Linear 评论区经常包含：

- 产品需求或设计说明
- 原型与附件
- 验收标准和测试补充
- 对正文的修订或否定

因此必须按时间顺序审阅全部评论、附件和关键文档，不能只看 issue description，也不能只看关键词命中的评论。

## 评论分层阅读协议

「读完全部评论」在评论上百条时会与上下文预算直接冲突。两种失败方式都要避免：因为量大而跳读，以及一次性把全文灌进上下文然后被截断。

可行的做法是分层，先取索引行（序号、作者、时间、长度、需求信号、是否已 resolve），再按层决定读法：

- **逐字读**：带需求信号的、含链接的、最早 3 条、最新 5 条，以及全部人类作者评论。
- **只登记不逐条读**：可判定为集成/机器人的评论，按类汇总，例如「bot 评论 47 条（PR 同步与部署通知），未逐条读」。
- **超长评论**：先读首尾各一段定性，确认相关再读全文。
- 上下文不足以按上述规则读完时停止并报告，不要静默降级成摘要。

已 resolve 的线程标注为「已关闭讨论」。它的结论不自动作为当前口径——需要在正文或未关闭线程里有对应落实，否则只能算历史讨论。

审阅输出要能被复核：评论总数、人类/bot 拆分、已逐字读的序号区间、汇总登记的序号、分页完整性标志。给不出这些数字就说明没读完。

## 文档与附件的降级

不可读来源（Linear document、上传附件、登录墙后的外部文档）不能凭标题或 URL slug 推断内容，但也不应直接终止：

1. 正文/评论已有等价口径（期望 + 验收标准 + 落点线索）→ 记为参考性缺口，可继续，登记进理解卡与 PR body 的「假设」段。
2. 它决定实现（期望或验收标准只存在于该文档）→ 一次性结构化索取，不反复追问。
3. 用户明确同意「按正文与评论口径实现」→ 可继续，但必须在理解卡、PR body 和收尾报告三处同时登记「该文档未核对」。

## 冲突处理

较新的评论不自动拥有覆盖权。只有出现“最终方案”“以此为准”“旧方案取消”等明确证据，才能作为候选最新口径；否则应列出冲突并询问用户。

## 项目标识与输入

Linear identifier 应优先使用完整形式，例如 `ENG-123`。不同项目的 team key 不同，Skill 不应写死团队 key。

裸数字输入仅在显式配置 `LINEAR_TEAM_KEY` 时才可补全：

```bash
export LINEAR_TEAM_KEY=ENG
```

未配置时应询问，而不是选择任意团队。

### 可变参数

除 `--base <branch>` 外还有三个用于收窄副作用与落点的开关：

| 参数 | 作用 | 典型用途 |
|---|---|---|
| `--dry-run` | 只产出审阅卡、理解卡和实施计划，不创建 worktree、不改代码 | 先确认口径，或只想要一份需求理解 |
| `--no-pr` | 做到提交并 push 任务分支为止，PR 标题与 body 只输出文本 | 仓库要求人工建 PR，或想先自查再开 PR |
| `--worktree-root <path>` | 指定 worktree 存放根目录 | 默认的仓库父目录不可写，或团队约定统一存放位置 |

`--dry-run` 的边界就是计划闸门：计划展示完即结束，不进入 worktree 创建。不要把它理解成「跑一遍但不提交」。

出现未知参数、重复冲突开关或多个 identifier 时应停止，不猜测其中哪个是本次目标。

## 代码落点

同一仓库可能存在旧版/新版页面、平台覆写组件、生成代码或多个服务实现。必须从实际路由、注册关系和 import 沿调用链确认真实生效文件，避免只按同名文件或关键词判断。

分层名称因项目而异。报告应使用代码真实存在的层次，例如 controller/use-case/adapter、route/handler/service/repository，不能把某种架构模板强加给所有项目。

## Git 基线与隔离

通用解析顺序：

1. 用户显式给出的 `--base <branch>`。
2. 目标仓库的 `AGENTS.md`、贡献指南或其他明确工作流文档。
3. 远程默认分支和已有 PR 约定。
4. 仍有歧义时询问用户。

确认后：

- `git fetch origin <base>`
- 显式以 `origin/<base>` 为 worktree base
- 在独立任务分支/worktree 中修改
- 主工作区 dirty 时不做 reset/clean/stash
- PR base 使用同一个已确认基线

不要假定每个项目都使用 `dev`，也不要假定任务分支只能叫 `feature/*` 或 `fix/*`；优先遵循仓库规范。

## 执行期参数固化

**每次 `bash` 工具调用都是一个新 shell，环境变量不跨调用保留。** 这不是风格问题，是两个具体事故的成因：

- 上一次调用里赋的 `WT` 在下一次为空，`cd "$WT"` 变成 `cd ""`，随后的 `edit` 直接改到主工作区。
- 上一次调用里赋的 `BR` 在下一次为空，`git push -u origin "$BR"` 退化成无 refspec 推送，可能一次推出多个分支。

因此计划确认后立刻把参数写成一份常量文件（`umask 077`），内容至少包括 identifier 及其小写变体、base、分支名、仓库根路径、worktree 路径、Issue JSON 落盘路径：

```bash
ENVFILE=/tmp/pi-linear-to-pr-<issue-lower>.env
(umask 077; cat > "$ENVFILE" <<'EOF'
ISSUE=ENG-123
ISSUE_LOWER=eng-123
BASE=develop
BR=fix/eng-123-short-slug
EOF
)
```

之后每个 bash 片段的首行固定为 source 该文件并断言必需变量非空：

```bash
set -euo pipefail; . /tmp/pi-linear-to-pr-<issue-lower>.env
: "${ISSUE:?}" "${BASE:?}" "${BR:?}" "${ROOT:?}" "${WT:?}"
```

配套约定：

- git 命令一律 `git -C "$ROOT"` 或 `git -C "$WT"`，不用裸 `git`，不把 `cd` 当作工作目录的唯一保证。
- 推送只用显式 refspec 一种写法，不依赖 `push.default`。
- 全程禁用分页器与交互提示，`diff`/`log`/`show` 加 `--no-pager`，CLI 显式传全参数。
- 大小写变体在参数文件里显式给出，不用 `${VAR,,}` 这类 bash 4 专有语法。

## 断点检测与恢复

同一个 Issue 被跑第二遍是常态：上一轮可能在验证失败、网络中断或用户叫停处停下。创建任何东西之前先探测残留，判定归属，再决定复用还是停止。

| 探测结果 | 处理 |
|---|---|
| worktree 已注册但目录不存在 | prune 后继续 |
| 本地分支存在，且其 commit 全部属于本 Issue | 复用，跳到验证步骤复验 |
| 本地分支含无关 commit，或不是已确认 `origin/<base>` 的后代 | 停止，让用户决定；不自行删除分支或 worktree |
| 远程已存在同名分支 | 停止并报告其作者与时间，可能是他人分支 |
| PR 已存在 | 交由 PR 步骤判定复用还是停止，不重复创建 |

判定为本次任务残留时**必须恢复**，不能要求用户先手工清理再从零重跑——那等于把工具的状态管理成本转给人。归属不明时相反：停止询问，不做任何删除。

不要用更危险的操作兜底。失败时保留 worktree、分支和 commit，并如实报告当前处于哪一步。

## 自动 PR 的授权边界

用户确认需求理解卡和实施计划后，Skill 可在验证通过后自动：

- 提交本任务文件
- 推送本任务分支（不 force）
- 创建到已确认 base 的 PR

授权不包括：

- 直推受保护分支
- force push
- 合并、approve 或 ready PR
- 回写 Linear
- 发布、部署或操作生产环境

`--no-pr` 只收窄授权范围（到 push 为止），不放宽任何一条禁止项。

授权是对**某一版计划**的授权。base、分支、改动文件集合或验收标准发生实质变化时旧授权失效，需要重新确认一次。

需要注意一类不受本 Skill 控制的副作用：仓库启用了 Linear 的代码托管集成时，分支名或 PR 标题里的 identifier 会触发集成自动关联 PR 并推进 Issue 状态。这是集成行为而非 Skill 的写操作，但必须在展示计划时一并告知，用户要求避免时改用不含 identifier 的分支名与标题。

## 验证

Skill 应从目标项目读取实际命令，例如：

- `package.json` / workspace scripts
- `Makefile` / task runner 配置
- `go.mod`、`Cargo.toml`、构建文件
- `AGENTS.md` / `CLAUDE.md` / contributing guide

报告必须区分已通过、失败和未执行的验证，不应把某个项目的命令当作通用默认。

改动跨多个包时按包逐一验证，每包都要有结论。根目录一条聚合命令不能代替逐包验证，只跑其中一个包也不能宣布通过。测试失败时先在未改动的基线上尝试复现：能复现才可能是 flaky，不能复现就按「本改动引入」处理，停止，不提交也不推送。

## 凭据

Linear API key 可来自：

1. `LINEAR_API_KEY`
2. `LINEAR_API_KEY_FILE`
3. `~/.config/pi/linear-api-key`

文件权限建议为 `600`。不要把 key 放入 Git、日志、PR body 或会话文本。

## references/ 分层

流程写全就会长到没人复核，写短就会丢掉真正踩过的坑。折中办法是把低频、长篇的执行细节从 `SKILL.md` 移到同目录的 `references/`，由对应 Step 显式引用，模型按需读取：

| 文件 | 内容 | 被哪一步引用 |
|---|---|---|
| `worktree-setup.md` | 参数固化约定、submodule、锁定模式依赖安装、codegen 引导 | 创建 worktree 后的环境引导 |
| `verification.md` | 逐包命令形式、时间预算、flaky 判定路径、无测试框架时的降级 | 验证 |
| `pr-output.md` | commit message 与 PR body 模板、fork 场景、脱敏规则 | 提交与创建 PR |
| `recovery.md` | 断点探测命令、归属判定表、push 被拒和并发处理 | 预检、创建 worktree、提交与收尾 |

两条维护约束：`SKILL.md` 里出现的每个 `references/*.md` 指针都必须真实存在，且 `references/` 下的每个文件都必须被 `SKILL.md` 引用——没有被引用的参考文件永远不会被加载，等于死代码。结构测试会同时检查这两个方向，以及参考文件本身是否单薄到不值得独立成文。

分层不改变闸门位置。参考文件只承载「怎么做」，「什么时候必须停下来问」始终留在 `SKILL.md`。
