# capability-research 设计说明

## 为什么需要它

“这个能力在什么情况下会触发、哪些配置会影响它”这类问题，单靠读代码得出的答案往往**长得很对，但实际不对**。首次实战（一个多平台网关里账号之间的故障转移）中，读代码得出、后来被实验推翻的结论有好几条：

- 处理函数里写死的上限是 3，但部署配置的默认值是 10，后者才是真实上限；
- “第二个请求跳过了坏账号”看起来是惩罚生效了，其实是粘性会话把请求粘到了上次成功的账号上；
- 一个“被信任的资源不受内存冷却影响”的承诺，单测里成立，真实调度链路上却不成立：调度读的是缓存快照，快照只保留了部分字段，信任开关正好不在里面；
- 红队用单测“证实”的一个结论，被主持者的对照实验推翻了。

所以这个 skill 的结构，围绕“证据从哪里来、谁有资格下结论”来设计，而不是围绕“怎么搜代码”。

## 三个角色

| 角色 | 职责 | 为什么要分开 |
|---|---|---|
| 蓝队（并行，按维度拆） | 读代码，产出带 file:line 的规则表 | 把大量文件阅读放在子上下文里，主上下文只接收结论 |
| 实验（主持者亲自做） | 隔离实例 + 可控上游桩，跑场景矩阵 | 实验是唯一能区分“应该这样”和“确实这样”的手段，不外包 |
| 红队（与蓝队不同上下文） | 拿着报告和实验数据，专门推翻 | 蓝队读代码时的盲区，自己复核时还是同一个盲区 |

主持者负责最后的裁决。红队并不天然正确：它的单测证据可能用的是一个字段完整、但线上拿不到的对象。

## 关键设计取舍

1. **Phase 0 一次问清范围和读者。** 首次实战里，用户在拿到文档以后才补充“只关注 API Key 类型”“要给外部看”，结果有一半篇幅要删，还得另写一版。把这两个问题提到最前面，代价只是多问一句。
2. **实验与蓝队并行，并且中途补发事实。** 实验发现“所有降级写入默认被拦截”这类前提性事实时，立刻发给每一路蓝队，否则它们交上来的“副作用”列整列都要重写。
3. **上游桩用凭证选择行为。** 被调研系统会把每个资源自己的凭证原样带给上游，这是控制“第几个资源返回什么”最便宜的办法，不需要改被调研系统的任何代码。
4. **两份文档，内部版不动。** 内部版是证据底稿，对外版是改写稿。用户对对外版的要求（不写过程、不写证据标签、不暴露实现、不写风险）全部收进 `references/external-doc.md`，并用禁词扫描兜底：通读挡不住“换个说法暴露实现”，扫描至少能挡住字面泄露。
5. **允许写，但写边界很窄。** 它不属于“只读”的开发审计类 skill，因为它必须写报告、起实例。写边界在结构测试里用固定短语钉死，参见 `tests/package-structure.mjs` 中的 `requiredCapabilityResearchRules`。

## 首次实战踩过的环境坑（与具体项目无关的部分）

- 项目的任务编排工具因为 worktree 里存在重名项目而解析失败。查到它的重启目标本质上就是一条进程管理命令后，直接执行这条等价命令，并在交付说明里写明。
- 更新代码时被几个未跟踪文件挡住。比对后确认是旧草稿，就移到备份目录，没有删除。
- 共享数据库服务器的连接数接近上限。隔离实例的连接池要压小，否则会连累其他服务。
- 出站安全策略拒绝回环地址，上游桩要绑到私网网卡上。
- 危险命令拦截钩子会扫描整条命令文本，含“强删 + 绝对路径”字面量的命令整条都不会执行。
- 浏览器截图工具反复返回旧画面时，改用 DOM 文本作为证据，不在截图上耗时间。
