# 让运营交付结算数据不再靠每周手工截图拼表

> 状态：待需求方确认 ｜ 更新于 2026-10-14 ｜ 收敛轮数 2

## 问题
运营同学每周需要向**外部采购方**交付一份结算数据用于核对。因为结算后台只有「按租户 + 月份读列表」这一个只读接口、没有任何导出或落文件能力（`repo/src/routes/settlement.ts:6` 注释明写「没有对外导出的能力」），运营只能在后台手工截图、再拼成 Excel 发给对方，一次约 30 分钟、每周重复一次，导致每周约 0.5 人时的重复人工投入。[来源：需求方第 2 轮原话「客户不是内部的人，是外面的采购方，说是拿去做核对用的」「现在是我们运营每周自己在后台截图、拼个 Excel 发给他，一次大概半个小时」；代码取证见「现状」]

> 未确认、不得当作事实的部分：现有手工流程是否出过漏行、超时或数据不全（第 2 轮回答「别的我说不好」）→ 未决 Q7。因此本 spec 不写任何基于「人工拼错」的损失。

## 目标结果
- G1 运营同学不再需要每周手工截图拼 Excel 才能交付结算数据；同一件事从「人工拼接」变成「系统取出」。[来源：由需求方原话给出的绕行方式与其成本推导；需求方原话为「每周…截图、拼个 Excel」，绕行成本即损失]
- G2 交付给外部采购方的结算数据严格限于该次交付对应的租户，不含其他租户的行。[来源：现网既有的租户隔离口径 `repo/src/routes/settlement.ts:8`（`req.user.tenantId`）+ 需求方第 2 轮原话「跨租户那个我更不敢拍，得法务和安全点头」——即跨租户不是已获准的行为]

## 现状（代码取证，先于提问完成）
- 仓库：`repo/`，Node + TypeScript，多租户 SaaS 结算后台（`repo/AGENTS.md`：「每个租户只能看自己的数据」）。
- 入口：`GET /settlements` — `repo/src/routes/settlement.ts:7`。
- 生效实现：`res.json(await listSettlements({ tenantId: req.user.tenantId, month: req.query.month }))` — `repo/src/routes/settlement.ts:8`。
- 当前行为：只读当前登录租户（`req.user.tenantId`），按 `req.query.month` 过滤；无导出、无落文件、无下载能力。同文件 `:6` 注释亦明写。
- 新增性：全仓只有两个文件（`AGENTS.md`、`src/routes/settlement.ts`）；`src/services/` 目录存在但为空；全仓 grep `export|csv|download|导出` 只命中 `settlement.ts:4` 的模块导出与 `:6` 的注释。不存在「其实已经有、只是入口深」的情况 → **导出是新增能力**。
- 取不到的：`listSettlements` 的服务层实现不在本次检出中（`src/services/` 为空），因此**它实际返回哪些字段无法从代码取证** → 未决 Q1，不猜。

## 候选方案
- 候选 A **一次性人工交付**：用一次性只读查询按指定租户 + 月份取数、生成文件、经现有渠道发给客户；代码库不动、不进仓库、不做入口与权限。
- 候选 B **产品化导出能力**：在结算后台新增导出（接口 + 页面入口），由运营自助完成。
- 候选 C **两者都要**：先用 A 救急，B 另立 spec。
- 本 spec 的起草口径：**暂按 B 起草**。理由只有一个且可指回原话：需求方给出的现状是「每周」重复发生的（原话），A 无法消除每周重复的那 30 分钟。但这属于业务投入取舍，需求方明确表示定不了（原话「我也不知道，这个我定不了，得你们看着办」），**不作为已定结论**，列为确认清单第 1 条；若答复选 A 或 C，本 spec 的 AC1–AC5 需整体重写，且「这次客户那份文件谁去交」需另定。
- 第 1 轮提问中出现的 CSV / UTF-8 带 BOM / xlsx、列清单、「谁点谁下」等都是**候选选项**，需求方明确未确认（原话「这些我一个都定不了，得客户说了算，你去问客户吧」），一律不作已定项。

## 约束（非功能）
- 性能：**不写阈值**。行数、跨月范围、期限未知 → 待补，见未决 Q3。
- 权限：导出范围必须沿用现有租户隔离口径（`repo/src/routes/settlement.ts:8`）；跨租户在法务与安全给出结论前不做（AC4、AC5）。
- 兼容 / 格式：待补，由客户定。注意：CSV / UTF-8 带 BOM / xlsx 是第 1 轮我给的候选选项，需求方未确认，不得据此写约束。
- 数据迁移：不相关 —— 只读现有结算数据，不改变存储结构。
- 可观测性：不相关 —— 需求方未提出任何日志或审计要求，且不阻塞 G1。（若最终选候选 A，运营侧「给谁导了什么、什么时候」的记录属于 A 的交付内容，见确认清单 E1。）

## 反向推演
- 情形一：导出做出来了，但列/口径跟客户核对的方式对不上，客户仍然要人工再处理一遍 → 已补 AC2（列按客户清单逐列一致）；用途细节未讲清的兜底在未决 Q4，不给 AC。
- 情形二：系统能导出，但运营还是得手工把文件发给客户，每周 30 分钟没消失 → 已补 AC1（G1 要求同一件事由系统取出）；发送环节本身列范围外（第 1 条）。
- 情形三：客户要的列里有结算后台并不存在的字段（例如对方系统自己的编号） → 列入范围外（第 2 条的延伸，开发者建议排除，待确认）；具体缺哪些列取决于未决 Q1/Q4，不预先补 AC。
- 情形四：一次要对核的数据跨多个月或跨多个租户，单租户单月导出交不清 → 跨租户列入范围外（第 3 条，待确认）；跨月列入范围外（第 4 条，待确认）。
- 情形五：导出过程中间失败或重复点击，产生半份文件或两份文件 → 未决 Q7 未答（是否出过超时/不全），无取值可写错误路径 AC；**不补 AC**，待 Q7 回答后再定。处置登记于未决 Q7。
