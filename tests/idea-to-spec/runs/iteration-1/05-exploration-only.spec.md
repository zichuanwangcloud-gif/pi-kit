# 探查：历史图片的引用方式与迁移落点（老域名 2027 年到期）

> 状态：探查　｜　时间盒：待补（见未决问题 Q0 —— 补齐前不开工）　｜　更新于 2026-10-13　｜　收敛轮数 2

## 背景问题

老系统目前仍在正常运行，上面的图片现在也点得开；问题不在老系统，而在它挂的那个老域名——域名 2027 年到期，
需求方不打算续费，到期后这些图片链接会全部打不开，历史图片就"以后没法看了"（用户原话）。

需求方想要的是把老图片迁进"现在这套系统"里，"能让这些老图正常显示出来就行，跟现在看到的一样"（用户原话）。

但"迁过来"这个方案能不能真的解决问题，取决于一个目前谁也不知道的事实：老系统里的图片到底是怎么被引用的
（绝对的老域名 URL、相对路径、独立图床域名、还是接口下发）。需求方对此的答复是"我也不清楚，得你们查了
才知道"（用户原话）。如果引用里带着老域名，那么仅把图片文件搬进新系统并不能让那些引用重新可用——
这正是本次探查要先弄清的事。

受影响者：老系统历史图片的查看者。具体是谁、在什么场景下来看（老系统页面里翻、还是从过去发出去的内容点进来），
需求方未说明 → 待补。

## 结论 → 下一步

- 若 Q1 结论为引用是相对路径或与域名无关，且 Q3 的引用点都在老系统内部 → 老链接失效的问题并不存在。
  此时按功能型 spec 写"把老图片导入现有系统图片库并能在内容中被引用"即可。
- 若 Q1 结论为引用里带老域名，且 Q3 存在"不可改写"的引用点 → 先由 C1 拍板（在老域名上做跳转 / 接受这批
  链接失效），再按拍板结果写功能型 spec；选"保住"时，"老链接仍能打开"必须写成 AC，不能当成隐含假设。
- 若 Q2 的数字显示需要分批迁移 → 功能型 spec 需补分批导入与失败重试的 AC（分批的阈值等 Q2 拿到数字后再定）。
- 若 Q4 显示老图片缺少现有系统必需的元数据 → 功能型 spec 需补元数据补全或占位策略的 AC。
- 若 Q4 显示现有系统的图片库与老图片的引用方式无法对齐 → 回到本流程与需求方重新确认落点，必要时重切范围。

## 范围外

- 老系统本身的改造与下线：不做 —— 老系统仍在正常运行，需求方明确"不是要停机下线"。
- 视频、附件等非图片资源的迁移：后续 —— 需求方只提到图片，是否包含待 C4 确认。
- 老图片的元数据治理、去重、画质修复：不做 —— 需求方的要求是"跟现在看到的一样"，不含变更好。
- 老系统页面在新系统里的整体重建：不做 —— 需求方要的是图片能显示，不是把老系统搬一遍。
- 探查期间的生产实现与上线：不做。
- 老域名续费与否的决定：不做 —— 属业务决策，见 C1。
