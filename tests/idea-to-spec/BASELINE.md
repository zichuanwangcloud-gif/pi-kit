# 基线发现（第 1 轮）

跑测时间：2026-10-13。8 个用例，7 个产出 spec，1 个（02）正确拒绝成文。

## 一、跑测基建的两个缺陷（我自己的错，先修）

### 1.1 沙箱路径被并发 session 污染 ⚠️ 严重

**现象**：用例 04 第 3 轮写出的 spec 被**另一个 session 覆盖**成了别的主题。
本机同时有 10+ 个 `claude --dangerously-skip-permissions` 会话在跑，共用
`/tmp/idea-eval/<slug>/work/` 同一路径。跑测 agent 靠比对 transcript 里的 Write 参数才恢复了真品。

**根因**：我把跑测产物放在固定路径 `/tmp/idea-eval/<slug>/work/`，而这个目录名会被别的会话撞上。

**修法**：每个 run 用独占目录，路径里带 run-id 与进程无关的随机段：

```text
/tmp/idea-eval/<run-id>/<slug>/{public.md, work/}
```

`<run-id>` 在跑测开始时生成一次（例如用启动时间 + pid），整个 run 内所有用例共用，
但不同 run 之间互不干扰。跑测开始时先断言目标目录不存在。

**还要加一致性校验**：交回前比对「本轮报告声明的 spec 路径」与「实际落盘文件的 mtime/hash」，
不一致就判本次运行作废，而不是拿去评分。

### 1.2 手动跑测与 workflow 跑测并行，互相覆盖 ❌ 已发生

我在起 workflow 之前，已经用 SendMessage 手动跑了用例 01 和 02 的第 2 轮。
两者写同一路径，结果只能保留一个。

**教训**：同一用例同一时刻只能有一条跑测链路。下一轮开始前先清空 run 目录并确认没有旧链路。

## 二、skill 的真实缺陷（这才是要改的）

按 linter 聚合：score 从 60 到 100，**平均 78.7**（不含未产出的 02）。
错误集中在三类，且都是**同一个根因的三个侧面**：

### 2.1 `PLACEHOLDER`（4/7 个用例命中）——模板填空癖

残留「待定」「同上」。这是模型在**把模板当表格填**：字段必须填满，于是填「待定」。
「同上」更严重，它意味着 AC 之间的独立断言点被合并了。

### 2.2 `REVERSE-UNPROCESSED`（1 个）+ 反向推演措辞不受控

用例 04 反向推演写了 6 条，用了「无法补成 AC」「已由 AC3 覆盖」这些**意思对但措辞不匹配**的说法。
linter 只认「已补 AC」「列入范围外」。
——这一半是 skill 的错（没规定固定措辞），一半是 linter 太死（应接受语义等价的说法）。

### 2.3 幻觉：把猜测从 AC 正文搬进「例子」列（用例 04，最严重）

评委原话：

> 它把「猜」从 AC 正文搬进了例子列和 `[推断]` 标签——为了让每条 AC 都带上具体取值例子，
> 它自造了阈值、期间、文件格式和脱敏列清单，正好命中本用例的核心陷阱。

具体编造：`耗时 ≤ 5 分钟`（凭空把 30 分钟基线除以 6）、`2026-09 结算期间`、
`.xlsx 或 .csv` 格式、一份待脱敏列清单。

**这是新加进去的「每条 AC 配具体例子」规则带来的反效果**：规则要求例子必须具体，
模型就自己造具体值来满足规则。**我的规则被它当成填空题做了。**

### 2.4 用例 05：探查型 spec 完全不套模板（score 64）

缺少「验收标准」「反向推演」「约束」三个段。探查型 spec 用了自己的结构，
但 linter 期望功能型结构。**一半是 linter 的错**（应识别探查型并换一组检查），
**一半是 skill 的错**（探查型模板没规定必填段）。

### 2.5 用例 08：AC 句式判定过窄（score 60，4 个 error）

「在任一已纳入的语言下，……不应当超出其父容器的边界」——这**是**合法的 EARS
（`在<状态>期间` 变体），但我的正则没覆盖「在……下」这种写法。**linter 的错。**
