# 评测夹具待修问题

优先级从上到下。

## 1. 「拒绝成文」被误判为「未产出」（已确认，必修）

**现象**：用例 02（加个导出按钮）里，skill 判定「字面诉求已被满足」→ 触发「立即停止并询问」→
不写 spec。workflow 里这类结果 `specPath` 为空 → `judge` 为 null → 不计入均分。

**为什么是 bug**：正确地拒绝成文，比写一份把方案当需求的 spec 好得多。当前口径让它既不扣分也不加分，
等于奖励「无论如何都产出一份东西」，与 skill 的立场相反。

**修法**：对 `status` 为 `stopped`/`exhausted` 的用例也起评委，换一组问题：

- `correct_block`：停止的理由是否成立（对照 hidden 判断：这个用例是否真的信息不足 / 是否真的已存在）？
- `false_stop`：是否过早罢手（其实再问一轮就能收敛）？
- 产出与不产出分开统计，报告里两个数都出：
  - `produced` 组按 recall/precision/scope/acceptability 打分
  - `refused` 组按 correct_block/false_stop 打分

## 2. 无仓库上下文让自检 ⑤ 恒失败（已确认，必修）

**现象**：沙箱里没有业务代码，所以「已定位唯一落点」这一项在每个用例都必然未通过。
这让所有用例的缺口数都至少是 1，掩盖了用例之间的真实差异（用例 01 就是这么变成 `草稿` 的）。

**修法**（二选一）：
- **给每个用例配一个最小桩仓库**（推荐）：每个 case 目录下加 `repo/`，
  放几个文件 + 可选 `AGENTS.md`，让取证这一步有真实的对象。
  用例 02 尤其需要——它的核心就是「去代码里查一下导出功能是否已存在」，
  没有代码这个用例根本没测到点子上。
- 或：评分时把 ⑤ 单列为「环境限制」，不计入缺口数，并在报告里显式声明。

## 3. 状态（可开工/草稿）与质量是两个维度（已确认）

用例 01 产出 `草稿`（缺口 1 = ⑤），但内容质量很高（linter 100 分）。
不要把状态当分数用，报告里分开呈现。

## 4. 评委看不到对话，可能低估「问得好但没写全」（假设，待验证）

评委只看 spec + hidden，看不到对话过程——这是有意设计（防止被措辞说服）。
但如果 skill 问出了某个事实、却在 spec 里没写，评委判它「漏了」，这对 skill 公平；
反过来，如果 skill 没问到但猜对了，评委判它「对」，这对 skill 有利。
后一种情况需要靠 precision 的「来源标注」检查来兜住：猜对了但没标 `[推断]` 的，应判幻觉。
**待验证**：下一轮跑完看 precision 是否真的抓住了这类情况。

## 5. 沙箱路径被并发 session 污染（已确认，必修）

**现象**：用例 04 第 3 轮写出的 spec 被**另一个 session 覆盖**成了别的主题。
本机同时有 10+ 个 `claude --dangerously-skip-permissions` 会话在跑，共用
`/tmp/idea-eval/<slug>/work/` 同一路径。跑测 agent 靠比对 transcript 里的 Write 参数才恢复真品。

**修法**：每个 run 用独占目录 `/tmp/idea-eval/<run-id>/<slug>/`，`<run-id>` 在 run 开始时生成一次，
run 内共用、run 间隔离；开始前断言目标目录不存在。交回前校验落盘文件与当轮报告一致。

## 6. 被测方读取宿主会话历史，把真实用户提问当成输入（已确认，必修）

**现象**：用例 05 第 1 轮，被测 subagent 读了 `~/.claude/history.jsonl`，找到本会话里用户的真实
prompt（「我感觉还是不够优质，开启loop循环，增强idea-tospec的能力……」），把它当成本轮输入，
产出一份完全无关的 spec。整轮作废重跑。

**根因**：subagent 与宿主共享文件系统，`~/.claude/` 可读；禁令只列了 `tests/`、`hidden`、git 历史，
没覆盖会话记录。

**修法**：禁令补全 `~/.claude/`（history/transcript/memory）与一切 session 记录；
并要求 prompt 明确「输入只有给出的内容，不得用环境中其他线索推断用户意图」。

**残留风险**：文件系统层面无法真正隔离，只能靠禁令。要彻底隔离需在容器或独立 HOME 下跑跑测。

## 7. 自检缺口数与正文自相矛盾（已确认）

用例 05 自检写「缺口数 2」，实际未通过 1 项；用例 03 同样。skill 需要在写缺口数时
**数一遍未通过行**，而不是凭感觉给数。linter 已有 `SELFCHECK-GAPS-MISMATCH` 检查，但 skill
本身没遵守自己的规则。

## 8. workflow subagent 不写文件，spec 从未落盘（已确认，必修，已修）

**现象**：第 1 轮迭代评测跑满 40+ 轮对话，8 个用例只落盘 1 个 spec。基线时同样时长能出 7 个。

**根因**：workflow subagent 的系统提示明确要求
`Write report/summary/findings/analysis .md files. Return findings directly as your final assistant message`——
即**不要写文件，把结果作为最终消息返回**。我在 prompt 里说「写 spec 到 work/spec.md」，
agent 服从了自己的系统提示，只回一句「Writing it now.」，spec 从未落盘。

**修法**：spec 全文通过结构化返回值（`spec_markdown`）带回，由 workflow 脚本落盘。
不依赖 subagent 的文件写入能力。

**教训**：跨 agent 交付产物时，**不要依赖文件系统作为传递通道**。返回值是唯一可靠的通道。
另外：改动跑测链路时必须用小样本先验证「产物真的能拿到」，不能只看日志里有结果就假定成功。

## 9. linter 误报率过高，不能直接当迭代信号（已确认，部分已修）

迭代 1 复查时，linter 报的 error 里又有约一半是误报：

| 报出的 code | 实际情况 | 处置 |
|---|---|---|
| `AC-NOT-EARS` ×2（用例 08） | 「在任一语言下……不应当超出父容器」是合法 EARS | 已放宽句式 |
| `AC-SECTION-MISSING`/`REVERSE-MISSING`/`CONSTRAINTS-MISSING`（用例 05） | 探查型 spec 本来就不该有这些段 | 已加探查型分流 |
| `REVERSE-UNPROCESSED`（用例 04） | 写了「已由 AC3 覆盖」，是等价处置措辞 | 已接受等价措辞 |
| `AC-ORPHAN` ×2（用例 02） | 约束型 AC（支撑栏写「约束」），不是孤儿 | 已排除约束型 |

**结论**：linter 目前只能作为**提示**，不能作为**门禁**。每次迭代必须人工复核 error 列表，
把误报修掉后再看分数趋势。否则会去优化一个不存在的缺陷。

**下一步**：继续收集误报样本，等误报率降到可接受再考虑接入 CI 门禁。
在 `npm run check` 里它目前只验证 linter 自身自检（good/bad 两个样本），不校验真实产物。
