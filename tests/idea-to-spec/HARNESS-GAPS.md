# 评测夹具待修问题

优先级从上到下。

## 1. 「拒绝成文」被误判为「未产出」（已确认，必修）

**现象**：用例 02（加个导出按钮）里，skill 判定「字面诉求已被满足」→ 触发「立即停止并询问」→
不写 spec。workflow 里这类结果 `specPath` 为空 → `judge` 为 null → 不计入均分。

**为什么是 bug**：正确地拒绝成文，比写一份把方案当需求的 spec 好得多。当前口径让它既不扣分也不加分，
等于奖励「无论如何都产出一份东西」，与 skill 的立场相反。

**修法**：对 `status` 为 `stopped`/`exhausted` 的用例也起评委，换一组问题：

- `correct_block`：停止的理由是否成立（对照 hidden 判断：这个用例是否真的信息不足 / 是否真的已存在）？
- `false_stop`：是否过早罢手（其实再问一轮就能收敛）？
- 产出与不产出分开统计，报告里两个数都出：
  - `produced` 组按 recall/precision/scope/acceptability 打分
  - `refused` 组按 correct_block/false_stop 打分

## 2. 无仓库上下文让自检 ⑤ 恒失败（已确认，必修）

**现象**：沙箱里没有业务代码，所以「已定位唯一落点」这一项在每个用例都必然未通过。
这让所有用例的缺口数都至少是 1，掩盖了用例之间的真实差异（用例 01 就是这么变成 `草稿` 的）。

**修法**（二选一）：
- **给每个用例配一个最小桩仓库**（推荐）：每个 case 目录下加 `repo/`，
  放几个文件 + 可选 `AGENTS.md`，让取证这一步有真实的对象。
  用例 02 尤其需要——它的核心就是「去代码里查一下导出功能是否已存在」，
  没有代码这个用例根本没测到点子上。
- 或：评分时把 ⑤ 单列为「环境限制」，不计入缺口数，并在报告里显式声明。

## 3. 状态（可开工/草稿）与质量是两个维度（已确认）

用例 01 产出 `草稿`（缺口 1 = ⑤），但内容质量很高（linter 100 分）。
不要把状态当分数用，报告里分开呈现。

## 4. 评委看不到对话，可能低估「问得好但没写全」（假设，待验证）

评委只看 spec + hidden，看不到对话过程——这是有意设计（防止被措辞说服）。
但如果 skill 问出了某个事实、却在 spec 里没写，评委判它「漏了」，这对 skill 公平；
反过来，如果 skill 没问到但猜对了，评委判它「对」，这对 skill 有利。
后一种情况需要靠 precision 的「来源标注」检查来兜住：猜对了但没标 `[推断]` 的，应判幻觉。
**待验证**：下一轮跑完看 precision 是否真的抓住了这类情况。
