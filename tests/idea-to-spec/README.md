# idea-to-spec 评测循环：总览

这份文件是接手入口。评测目标、方法、各轮结果和未解决问题都在这里。

## 为什么有这个目录

`idea-to-spec` 的价值主张是「产出的 spec 可验证，而不只是听起来合理」。这个主张必须被检验，
否则它只是一句自我声明。本目录就是检验它的机器。

## 目录结构

```text
tests/idea-to-spec/
├── EVAL-PROTOCOL.md      三角色隔离、评分口径、评委协议 v1 与 v2（v2 取代 v1）
├── RUNBOOK.md            怎么跑：冒烟要求、隔离禁令、自动化编排
├── ITERATIONS.md         各轮改了什么、结果如何、规则如何被绕过
├── BASELINE.md           第 1 轮基线发现
├── HARNESS-GAPS.md       跑测基建的 10 个缺陷（含 5 次 linter 误报）
├── fixtures/
│   ├── SCHEMA.md         用例格式：public / hidden / repo 三段
│   └── cases/            8 个用例，每个含 public.md + hidden.md + repo/
├── lib/spec-lint.mjs     394 行确定性检查器（形式层）
├── selfcheck/            linter 正反例自检，已接入 npm run check
├── calibration/          植入已知幻觉的校准样本 + 答案表
├── runs/
│   ├── iteration-1/      8 份 spec + 对话还原 + 双评委结果
│   └── iteration-2/      2 份 spec + 对话还原（冒烟）
├── run-eval.workflow.js  跑测编排：对话循环 + 落盘
└── judge-v2.workflow.js  重评编排：校准 + 保真审计 + 3 评委取中位数
```

## 三层测量，缺一不可

| 层 | 工具 | 查什么 | 局限 |
|---|---|---|---|
| 形式 | `lib/spec-lint.mjs` | 句式、占位符、孤儿 AC、缺口数 | **查不出幻觉**（实测：linter 95 分 vs 评委 0.93） |
| 语义 | 评委 agent（v2） | 每条断言是否属实、来源是否成立 | 贵；必须校准 |
| 归责 | 需求方保真审计 | 漂移是模拟器造成的还是 skill 造成的 | v1 缺这一层，导致结论错误 |

## 各轮结果

### 基线（2026-10-13）
linter 均分 78.7。发现「例子要具体」的规则催生了编造具体值。

### 迭代 1（2026-10-13）
改动：具体值必须来自问到的、探查型模板、自检口径、桩仓库、跑测基建三修。

**v1 评委结论（后来被推翻）**：precision 0.685，8/8 用例都在「给编造内容贴权威标签」。
**v2 评委结论（修正后）**：precision **0.932**，每用例 skill 幻觉 **0.875**。
差异原因：v1 评委看不到对话，把需求方模拟器的即兴发挥（每用例 2.5 条）记成了 skill 的错。

### 迭代 2（2026-10-14）
改动：取证先于提问；六维「人的体验清单」（何时/谁多少/多严重/代价/有无报错/何时算好了）；
确认外溢与范围外扩张两条自查。

冒烟（用例 03、04）：recall 0.167→0.58、0.40→1.00（v1 口径）。
对话层直接可见：用例 04 里「采购」「法务/安全」「每周 0.5 小时」从迭代 1 的
**0 次出现** 变成迭代 2 都出现。

## 未解决

1. **确认外溢**（用例 02）：需求方只认了段落里一句，整段被标成「用户确认」。已写自查，未验证。
2. **范围外扩张**（用例 06）：顺口一句「那些以后再说」被写成整类排除，还混入自造项。已写自查，未验证。
3. **漏问未完全解决**：迭代 2 的用例 03 仍漏了 K5（瓶颈在哪）与「其余时段不劣化」。
4. **评委成本**：全量 8 用例重评约 220 万 token / 100 分钟。日常迭代应用小样本。
