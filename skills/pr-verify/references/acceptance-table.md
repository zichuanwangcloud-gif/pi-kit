# A 节：验收表——把需求翻译成字面断言

验收表是后续五节的唯一输入。它存在的理由：AI 面对含糊需求不会停下来问，会编一个合理的解释、实现它、再为它写出绿色测试。表把「解释」这个动作前移并暴露给用户裁决。

> 由 SKILL.md 的 A 节引用。B、C、F 节只读 `$TABLE`，不回头读 PR 描述。

## 需求来源与优先级

按顺序取，前者覆盖后者：

1. 用户在本次对话里明确给出的需求或裁决；
2. 关联 Issue / 需求文档正文（有链接就读原文，不读 PR 描述里的转述）；
3. PR 描述；
4. commit message。

来源之间矛盾时不取交集也不取并集：把矛盾列进「需要猜」栏。PR 描述里说「顺带修了 X」而需求没提 X 的，X 单独成行并标来源 `PR 描述`，C 节「范围二分」会用到。

## 表结构

```markdown
| # | 操作 | 输入 | 期望的字面结果 | 类型 | 来源 |
|---|---|---|---|---|---|
| 1 | POST /orders | {sku:"A",qty:2} | 201；body.total == 200；orders 表新增 1 行 status='pending' | 正向 | 需求 §2 |
| 2 | GET /orders/{id} 以另一租户身份 | 他人 order id | 404（不是 403，不泄露存在性） | 负向 | 需求 §5 |
| 3 | 关闭 flag orders.v2 后 POST /orders | 同 1 | 走旧路径：body 无 total 字段 | 负向 | 推断 |
```

- `类型`：`正向`（应该做什么）、`负向`（必须不做什么）、`非功能`（延迟、并发、容量——转 D/E 节）。
- 一行只放一个可观察结果；「返回 201 且落库且发邮件」拆三行。
- `操作` 写用户/调用方视角的动作，不写内部函数名。

## 期望列的写法

禁用词：正确、正常、成功、符合预期、合理、妥善处理、友好提示。出现即改写。

| 含糊写法 | 改写为 |
|---|---|
| 返回正确的总价 | `body.total == 200`（2 × 单价 100） |
| 校验失败时提示友好 | `400`；`body.error.code == "QTY_OUT_OF_RANGE"`；`body.error.message` 非空且不含堆栈 |
| 页面正常显示 | `#total` 文本 == `"¥200.00"`；`button[type=submit]` 可点击 |
| 支持全天时段 | 时间选择器 `input.value` 字面等于 `"00:00-24:00"`（原生 `<input type="time">` 表达不了 24:00，须先确认控件） |
| 性能可接受 | 转非功能行：「相对 base 的 P95 变化 ≤ 5%」 |

原则：期望值必须能被一条命令或一个断言读出来。读不出来的期望，要么补上读取手段（日志行、DB 查询、DOM 选择器），要么进「需要猜」栏。

## 负向行

验收表天然只写「应该做什么」。每张表至少检查四类负向行，适用的必须列出，不适用的写一行 `N/A + 原因`：

1. **权限**：无权限角色、跨租户、未登录访问新入口时的结果。
2. **开关**：feature flag 关闭 / 配置缺省时，新行为必须不出现。
3. **幂等**：同一请求重复到达两次（重试、双击、消息重投）时第二次的结果。
4. **泄露**：错误响应与日志里不得出现堆栈、内部标识、其他用户数据。

负向行在 B 节真跑时要同时给出「路径确实执行过」的痕迹（日志行、计数器），否则「没发生」和「没跑到」的绿色一样。

## 「需要猜」栏

表尾单列一段：

```markdown
## 需要猜（未裁决前本 Skill 不继续）
| # | 含糊点 | 候选解释 | 影响的行 |
|---|---|---|---|
| G1 | 「超时」没给数值 | 5s / 30s / 沿用全局配置 | 4, 7 |
| G2 | 需求说「管理员可见」，未说子管理员 | 含 / 不含 | 2 |
```

规则：

- 来源标 `推断` 的行自动进此栏。
- 候选解释至少两个；只列出一个说明并没有在猜，直接写进表。
- **此栏非空 → 停止并把整栏原样给用户**。用户逐条裁决后把结论写进对应行的 `来源` 列（`用户裁决 YYYY-MM-DD`），清空此栏再继续。
- 用户说「你看着办」不算裁决；记录原话并按最保守解释继续，同时该行 `来源` 标 `保守默认`，报告「未决问题」段复述。

## 独立上下文提取（推荐）

提取本身也应由独立上下文完成——本会话如果已经读过实施过程，会不自觉地按实现反推需求。给提取者的输入：需求来源原文、PR 描述、`$CONVENTIONS`；**不给** diff。提示词：

```text
把下面材料里声称要实现的每一条能力写成「操作 | 输入 | 期望的字面结果 | 类型 | 来源」表。
期望列禁止出现正确/正常/成功/符合预期/合理；必须是具体数值、字符串、状态码、DOM 值或状态。
每条能力补权限/开关/幂等/泄露四类负向行，不适用写 N/A 加原因。
凡是你需要猜才能写出字面值的地方，不要猜，单独列到「需要猜」表，给至少两个候选解释。
```

提取者输出回来后，本会话只做两件事：核对来源引用属实、把「需要猜」栏交给用户。

## 落盘

```bash
. /tmp/pi-pr-verify-<ID>.env; : "${PACK:?}" "${ENVFILE:?}"
TABLE="$PACK/acceptance-table.md"
[ -s "$TABLE" ] || { echo "STOP: 验收表未落盘到 $TABLE"; exit 1; }
GUESS=$(sed -n '/^## 需要猜/,$p' "$TABLE" | grep -c '^| G' || true)
printf "export TABLE='%s'\n" "$TABLE" >> "$ENVFILE"
echo "rows=$(grep -c '^| [0-9]' "$TABLE") guesses=$GUESS"
[ "$GUESS" -eq 0 ] || { echo "STOP: 需要猜栏有 $GUESS 条未裁决，交用户后再继续"; exit 1; }
```

`guesses` 非零时这段以 `STOP` 退出，是原则 3 的机器化形态；用户裁决后重跑它，为零才放行。
