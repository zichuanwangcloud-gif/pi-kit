# 蓝队 / 红队分工说明模板

分工说明是子 agent 唯一能拿到的上下文。写不清楚，它就会从零搜索，或者把主持者的猜测当成结论交回来。下面两个模板按需替换尖括号里的内容。

## 蓝队模板（代码调研）

```text
你在做一项只读代码调研：不改任何文件，不跑 git 写操作，不启动或重启服务。
仓库：<路径>（<技术栈一句话>；<项目特有目录约定，例如哪些是扩展代码>）。

目标：把 <实现族/维度> 在 <能力名> 上的完整判定规则调研清楚。
范围：<平台/资源类型/接口>；不在范围内：<明确排除项>。

已知起点（不用重新找）：
- 入口：<文件:行>
- 核心判定：<函数名 文件:行>
- 上限/常量：<文件:行>

必须回答（每条结论附 file:line，并引用关键代码原文）：
1. <触发条件逐项列出，例如各状态码 / 连接错误 / 超时 / 流式中途>：会不会 <行为>？先 <次级行为> 吗？有什么持久化副作用（字段、时长）？调用方看到什么？
2. <特判：关键词、条件分支>
3. 资源级配置的影响：精确到字段名和读取方法。说清楚打开后是从“会”变“不会”，还是反过来。
4. 单次请求内的上限、间隔、耗尽后的返回。
5. 项目自定义层对上述行为的改动及开关（名称、默认值、存储位置）。

输出：写入 <工作目录>/blue-<维度>.md。
结构：
- 先一张“触发条件 → 次级行为 → 主行为 → 副作用 → 调用方响应 → 证据”大表；
- 再一张配置影响表；
- 最后列“不确定 / 需要实测”的点。
最终回复只给文件路径和不超过 10 行的要点。
没看到代码证据的写“未证实”，不要猜。
```

### 写蓝队说明时的注意

- **给起点，不给结论。** 写“核心判定在 X”，不写“我认为 X 会导致 Y”。把假设交给子 agent，它多半会原样确认回来。
- 维度之间不要重叠。重叠的部分两路都会写，而且多半写得不一样，裁决成本会翻倍。
- 实验中途发现推翻常识的事实（例如“所有降级写入默认被装饰器拦截”），立即用消息补发给**每一路**相关蓝队，并要求它们按“原生会做 X；默认是否被抑制；需要什么开关”的口径改写副作用列。

## 红队模板（对抗复核）

```text
你是红队，任务是推翻一份蓝队调研报告里的错误结论。
只读：不改源码，不跑 git 写操作，不重启服务。
仓库：<路径>。

被审报告：<工作目录>/blue-<维度>.md
实测数据：<工作目录>/out-*.txt（说明每个文件对应什么场景，并说明已知的假象，例如“某文件第 2 次请求的结果是粘性会话造成的，已用另一个文件排除”）
场景定义：<工作目录>/sc/...；上游桩与驱动脚本：<文件名>

做法：
1. 逐条核验报告大表和配置表的每一行。能对上实测的，以实测为准；矛盾处指出谁对，并给出证据。
2. 重点攻击这些高风险点：<列出 4～7 个，优先选“只有代码证据”和“与实测看起来不一致”的条目>
3. 找遗漏：报告没写、但代码里会影响 <能力> 的分支。

输出：写入 <工作目录>/red-<维度>.md。
表格列：报告结论 | 判定（CONFIRMED/REFUTED/PARTIAL/UNVERIFIED）| 反证或佐证（file:line 或 实测文件+场景名）| 修正后的说法
然后列“遗漏项”。
最终回复只给路径和不超过 10 行的最重要推翻点。
没有证据不要下 REFUTED。
```

### 写红队说明时的注意

- **把实测数据给红队。** 只给报告的话，红队也只能读代码，和蓝队犯同样的错。
- 主动告诉它数据里已知的假象，否则它会拿假象去“推翻”正确的结论。
- 列给红队的攻击点里，至少放一个主持者自己也拿不准的点。

## 主持者裁决规则

红队交卷后，按这个顺序处理：

1. **红队说 REFUTED、实测支持红队**：采纳，写进“被推翻的说法”表。
2. **红队说 REFUTED、实测支持蓝队**：红队错了。照样写进表里，注明“红队的说法被实测推翻”。
3. **红队用单测或构造对象证明了某个行为**：查真实链路上被读取的对象是不是同一个。缓存快照、投影、DTO 往往会裁掉字段，单测里成立的事在线上可能不成立，反过来也一样。能做对照实验就做。
4. **双方都只有代码证据、而结论要写进对外文档**：补实验；做不了的，就不写进对外文档的“默认行为”。
5. **红队的遗漏项**：逐条判断是否在 Phase 0 确认的范围内。范围内的，补进报告，能实测的补实测。

裁决时发现的真实缺陷（实现与设计意图不符、承诺在某条链路上失效），单独记进内部报告的“发现的问题”，附上复现步骤。
