# 对外说明文档：写法与禁写清单

对外文档的读者是运营、客户成功、客户，或者不看代码的同事。他们只关心三件事：**会发生什么、为什么会这样、我能调什么**。至于结论是怎么得出来的、写在哪个文件里，他们并不关心，而且有些内容本来就不该给他们看。

## 1. 硬性规则

| 规则 | 说明 |
|---|---|
| 另存为新文件 | 内部证据报告原样保留，对外版从它改写，不在原文件上删改 |
| 不写调研过程 | 不提怎么调研的、派了几路 agent、做了对抗复核、用了什么浏览器工具或实验工具 |
| 不写证据等级 | 删掉所有“实测 / 代码 / 推断”之类的标签。不确定的内容不要写进对外版，而不是加个标签留着 |
| 只写确认过的范围 | Phase 0 说只关注 A 类资源，就把 B 类相关的行、列、段落全部删掉，不留“B 类暂不讨论”这种话 |
| 不写缺陷和风险 | “发现的问题”整节删掉。其中描述的**行为本身**如果对读者有用（比如“某接口全部失败时会直接返回 401”），改写成中性的使用提示保留 |
| 不暴露实现 | 不出现源码路径、文件名、函数名、行号、数据库表名和列名、设置项 key、配置文件 key、环境变量名、内部工单号、内部服务名 |
| 不写代码来源 | 不出现区分“哪部分是我们改的、哪部分是原有的”的词，例如分叉、二次开发、自研改造、上游实现、覆写、补丁、受控例外 |
| 名称用界面原文 | 配置项写成读者在界面上能找到的名字和路径，例如“账号管理 → 编辑账号 → 高级配置”；部署配置写清用途和默认值即可 |

部署配置项要不要写 key，取决于读者：给运维的版本可以单独附 key，给运营或客户的版本不写。拿不准时问用户。

## 2. 结构模板

```markdown
# <能力的通俗名称>说明

> 适用范围：<资源类型、平台>。
> 内容基于 <年月> 的版本整理。

## 一句话版本
<两三句话：默认会怎样，什么情况下例外，读者最该知道的一件事。>

## 一、先分清两件事
<把最容易混淆的两层机制用一张小表分开，比如“这一次请求内”和“后续请求”。>

## 二、<主维度>对照表
<先解释表里用到的几个词，再给主表；表后列 2～3 条“容易踩坑的地方”。>

## 三、<主维度>以外的情况

## 四、上限，以及全部失败时返回什么

## 五、<资源>设置里哪些会影响它
<每一项：在哪里找、打开后会怎样、和其他项的关系。>

## 六、系统设置里哪些会影响它

## 七、部署配置（需要运维改）

## 八、容易混淆的相邻功能

## 附：给<读者角色>的几条建议
```

不适用的章节直接删掉，不要留空标题。

## 3. 语气

目标是像一位熟悉系统的同事写给另一位同事的说明。

| 少用 | 改成 |
|---|---|
| “本文档旨在全面阐述……” | 直接说结论 |
| 每句都加粗、到处是 emoji 和箭头符号 | 只给真正要紧的那一两处加粗 |
| “值得注意的是”“综上所述”“总而言之” | 删掉，或者改成“注意”“简单说” |
| 被动、抽象：“该机制会被触发” | 主动、具体：“网关会换个账号再试” |
| 堆砌三段式排比 | 一件事说一遍 |
| 表格里每格都写满 | 意思相同的格子合并成一行文字说明 |

可以用一点拟人化的说法帮助理解，比如“默认很宽容”“先让它歇一会儿”“它会耐心地试 5 次”。但不要用夸张的形容词，也不要故作俏皮。

## 4. 禁词扫描

写完必须扫描。禁词正则按下面几类组装，命中一个改一个，直到扫描通过：

| 类别 | 例子（按项目实际情况补充） |
|---|---|
| 调研过程 | `红队`、`蓝队`、`红蓝`、`对抗`、`实测`、`推断`、`【代码】`，以及用到的工具名 |
| 代码来源 | `二开`、`二次开发`、`上游改动`、`覆写`、`补丁`、`受控例外`、项目内部命名空间 |
| 实现细节 | `\.go`、`\.ts`、`\.py`、`:[0-9]+`（行号）、`_`（下划线标识符，多数是字段名或 key）、数据库列名、设置 key 的前缀 |
| 范围外 | Phase 0 排除的资源类型、平台名 |
| 内部名 | 内部工单号前缀、内部服务名、内部架构组件名 |

下划线规则误伤很少：对外文档里本来就不该出现带下划线的词。真有必须保留的专有名词时，单独加白名单，不要放宽整条规则。

扫描通过后，再通读一遍，专门检查有没有**换了个说法、但仍在暴露实现**的句子。比如“调度时读取的那份缓存里少了这个字段”，虽然没有出现任何代码名，但描述的还是内部实现。这类句子要改写成读者能观察到的现象，例如“偶尔会被跳过一小会儿”。
