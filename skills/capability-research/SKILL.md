# Capability Research：证据驱动的能力调研

输入一个能力或机制（如“账号间故障转移”“限流回避”“缓存失效”），输出：

1. **内部证据报告**：每条结论都能追到代码位置或实验输出，含被推翻的说法和未验证项；
2. **对外说明文档**：去掉过程、证据标签和实现细节，只保留读者需要的行为与配置说明。

核心纪律只有一条：**拿到关键证据再下结论**。读代码得到的是“应该这样”，跑出来的才是“确实这样”。两者对不上时，以实验为准，再回头找出代码哪里读错了。

## 边界与安全

- 唯一的写操作是调研产物：报告、实验脚本、实验输出，全部放在调研工作目录（默认项目内已忽略的临时目录，或系统临时目录）。**不修改被调研项目的源码、配置和迁移文件。**
- 不 push、不提交、不创建或修改 PR、不部署、不写任何 Issue 系统。
- 不触碰主工作区的用户改动：不 reset、不 clean、不 stash、不覆盖未跟踪文件。需要更新代码而被未跟踪文件挡住时，先比对内容，确认是旧副本后**移到备份目录**，并在交付说明里写明，不删除。
- 实验只在**隔离实例**上进行：独立数据库或库名、独立缓存分区、自己起的上游桩。不连生产，不复用会把流量转到真实上游的共享数据，也不往共享开发库里写数据。
- 连接任何线上或测试环境之前，先问用户。
- 浏览器核对只看不保存：编辑弹窗一律点取消，因为“保存”本身可能把默认值写进去。
- 对外文档不覆盖内部报告，必须另存为新文件。

## Phase 0：确认范围（只问一次）

开工前一次问清，后面不再反复确认：

| 问题 | 为什么必须先问 |
|---|---|
| 调研对象是什么，用户关心的是“会不会触发”还是“触发后怎样” | 决定主表的行与列 |
| 范围：哪些平台、账号/资源类型、接口在内，哪些明确不关注 | 范围外的内容会占掉一半篇幅；用户后补“只关注 X”时，返工代价很大 |
| 文档读者是谁：只给自己/研发，还是要给运营或客户 | 决定是否要出对外版，以及对外版的禁写清单 |
| 是否允许在本机起隔离实例做实测；是否允许用浏览器核对界面 | 决定证据能做到多强 |

用户说“都要”“你看着办”时，按“全平台、两份文档都出、允许本机实测”执行，并在交付时说明这个默认选择。

## Phase 1：基线与项目约定

1. 先读仓库根目录和目标模块的 `AGENTS.md`、`CLAUDE.md`、贡献指南，记录服务怎么启动和重启、哪些目录只读、端口和数据库约定。
2. 确认调研基于的版本。用户要求“最新代码”时，用项目约定的方式同步（fast-forward 或项目规定的合并流程）。服务需要重启的，用项目规定的入口，只重启相关服务。
3. 记下基线提交，写进报告页眉。

```bash
git rev-parse --show-toplevel
git status --short --branch
git log --oneline -1
```

## Phase 2：拆维度，派蓝队做代码调研

1. 先花几分钟亲自摸骨架：入口、核心判定函数、上限常量、配置读取点。目的是能写出**有起点**的分工说明，而不是让子 agent 从零搜。
2. 按“彼此独立、合起来覆盖全部”的原则拆 3～5 个维度。常见切法是“每个实现族一路 + 配置/界面一路”。
3. 每路蓝队的分工说明按 `references/team-briefs.md` 的蓝队模板写，必须包含：
   - 已知起点；
   - 必须回答的问题清单；
   - 统一的输出表结构（触发条件 → 行为 → 副作用 → 调用方看到什么 → 证据）；
   - “没看到代码证据就写未证实”的要求。
4. 并行派出，各自把结果写成文件，回复里只带文件路径和不超过 10 行的要点。全文留在文件里，不进主上下文。
5. 等待期间不要闲着，去做 Phase 3 的实验。实验中发现的关键事实（尤其是推翻常识的）要**立刻**补发给相关蓝队，避免它们把错误前提写进结论。

## Phase 3：隔离环境实测

这一步决定报告的分量。做法见 `references/evidence-harness.md`。要点：

- **同一份代码起一个独立实例**，用独立库、小连接池、独立缓存分区，不影响共享开发环境。
- **自己写一个可控的上游桩**：用请求里的某个字段（如 API Key）选择行为，例如返回指定状态码、带关键词的错误体、直接断开、流式中途出错。每次被调用都追加一行日志，这样就能看到实际打了哪些上游、按什么顺序打的。
- **每个场景都新建一套隔离夹具**（分组、账号、调用凭证），避免上一个场景的状态污染下一个。
- **先排除混淆变量，再解读结果**。最常见的几个：
  - 粘性会话：相同内容连发会粘到上次成功的资源，看上去像“坏资源已被摘除”；
  - 内存冷却的阈值：比如连续 2 次失败才触发，只发 2 个请求就测不出来；
  - 默认值被保存动作写入：界面新建和编辑写入的默认值可能不同。
- 每个场景至少连发 2～5 次，同时看“本次请求内”和“跨请求”两层行为，并在实验结束后查一次持久化状态（数据库里的状态字段），与日志对照。
- 实验输出原样存成文件。报告里的每条实测结论，都要能指到具体的输出文件和场景名。

## Phase 4：红队对抗复核

蓝队交卷后，派**与蓝队不同上下文**的红队。分工说明按 `references/team-briefs.md` 的红队模板写：

- 给它蓝队报告、实验原始输出和场景定义；
- 任务是**推翻**，不是复核确认；
- 判定只能是 CONFIRMED / REFUTED / PARTIAL / UNVERIFIED，没有证据不许下 REFUTED；
- 必须单独列出“遗漏项”。

一路红队可以同时审两份关联较弱的蓝队报告；但核心实现族最好一对一。

## Phase 5：主持者裁决

红队的说法也可能是错的。下面三种情况，主持者必须**亲自**用代码加实验定案，不能直接采信任何一方：

1. 蓝队、红队、实测三者有任意两方矛盾；
2. 红队的证据是单测或构造对象：真实链路上拿到的对象可能被缓存、投影或裁剪过，字段不全；
3. 结论会写进对外文档的“默认行为”。

做法：

- 对矛盾点补一个专门的对照实验。例如“显式设置 vs 缺省”“连发 5 次 vs 2 次”。
- 实验和代码对不上时，顺着读取链找到真正被读的那个对象，确认字段有没有被丢掉。这类矛盾经常就是一个真实缺陷，要单独记录。
- 能在本机验证但成本高的，做；在本机做不到的（例如需要真实第三方凭据的链路），标为“未验证”，写明为什么做不到，不下结论。

把“最初说法 → 裁决 → 依据”整理成一张表，放进内部报告。

## Phase 6：界面核对（可选）

允许使用浏览器时，在**新开的标签页**里核对：

- 配置项的真实位置（所在菜单、标签页、折叠区）；
- 界面原文：直接取 DOM 文本，不凭 locale 文件推测，因为构建期可能改写文案；
- 默认状态。

不动用户已经打开的标签页。截图前确认目标标签处于激活状态；截图工具返回旧画面时，以 DOM 文本为准，不要在截图上反复耗时间。

## Phase 7：产出文档

### 内部证据报告

结构：

1. 结论速览（不超过 6 条）；
2. 机制分层（例如“单次请求内 vs 跨请求”）；
3. 主表（触发条件 × 实现族）；
4. 非主维度的触发条件；
5. 上限与耗尽时的返回；
6. 配置影响（按资源、全局设置、部署三层分开）；
7. 容易混淆的相邻能力；
8. 发现的问题；
9. 对抗中被推翻的说法；
10. 未验证项；
11. 复现方式。

每条结论都标证据等级：实测 / 代码 / 推断。

### 对外说明文档

用户要求对外版、或者 Phase 0 确认了读者是运营或客户时才写。规则见 `references/external-doc.md`，要点：

- 另存为新文件，不覆盖内部报告；
- 不写过程：调研方法、对抗流程、使用的工具一概不提；
- 不写证据等级标签；
- 只写 Phase 0 确认的范围内的内容；
- 不写缺陷和风险章节，除非用户明确要；
- 不出现代码路径、函数名、数据库列名、设置项 key、工单号，也不出现关于代码来源或分叉历史的词汇，一律换成界面上的名称或通俗说法；
- 语气像同事写给同事的说明，不像报告生成器。

写完必须跑禁词扫描，命中即修改，直到扫描通过：

```bash
DOC="<对外文档路径>"
BANNED="<按 references/external-doc.md 组装的禁词正则>"
HIT=$(grep -nE "$BANNED" "$DOC" || true)
[ -z "$HIT" ] || { echo "STOP: 对外文档仍含禁写内容"; echo "$HIT"; exit 1; }
echo "external doc clean"
```

## Phase 8：清理与交付

1. 停掉自己起的实例和上游桩：按端口查出 PID 后逐个结束，**不要用按命令行模糊匹配的方式批量结束进程**，那样可能误杀当前 shell。删除临时库，清空自己用过的缓存分区。
2. 保留实验脚本和输出，便于复现。删除大体积的二进制产物。
3. 交付说明里写清楚：
   - 两份文档的路径；
   - 最重要的结论（3～5 条）；
   - 发现的问题；
   - 未验证项；
   - 对环境做过的操作，例如移动了哪些文件、重启了哪些服务。

## 完成前检查

- [ ] Phase 0 的范围和读者已确认，或已写明默认选择。
- [ ] 每一条“默认行为”结论都有实测支撑；只有代码证据的，在内部报告里标了“代码”。
- [ ] 已排除粘性、阈值、保存写入这三类混淆变量，或说明为什么不适用。
- [ ] 红队与蓝队不同上下文；所有矛盾都由主持者用代码加实验裁决过。
- [ ] 被推翻的说法已整理成表；未验证项写明了原因。
- [ ] 对外文档是新文件，禁词扫描已通过，范围与 Phase 0 一致。
- [ ] 隔离实例、上游桩、临时库已清理；没有改动被调研项目的源码。
