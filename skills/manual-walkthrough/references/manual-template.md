# 手册写作模板与发布

## 章节结构

```markdown
## <编号> <页面中文名>
**适用角色**：超级管理员 / 主用户 / 子用户
**入口**：左侧菜单「xxx」→「yyy」（必要时写页面地址）
**用途**：两三句说明这页解决什么问题。

### 页面概览
![](img/<编号>-1.png)
一段说明页面布局：列表有哪些列、筛选条件、右上角按钮等。

### 操作：<动作名>
1. 第一步……
2. 第二步……
![](img/<编号>-2.png)
> 说明：字段含义 / 注意事项 / 不可逆提示。

### 注意事项
- ……
```

- 每个主要操作一节；查看类页面至少「页面概览 + 筛选/导出」两节。
- 多 Tab 页面（系统设置、平台设置、主用户详情）：每个 Tab 至少一张截图 + 该 Tab 内分节逐条说明，**不得只列标题**。
- 新建类操作（建主用户、建子用户、建 Key、生成兑换码）要真的做一遍，截表单和结果。
- 图片引用用相对路径 `img/xxx.png`；一级标题用 `##`。
- 术语以页面实际显示为准（页面写「API Key」「账号状态」「组织」「订阅份」就照抄）。
- 字段解释写用户能理解的话；开关类要写「开 / 关各代表什么」。
- 菜单不存在时：先去「系统设置 → 功能开关」或「平台设置 → 功能管理」看开关；打开后记录到「前置条件」。确实做不到的加 `> ⚠️ 本次走查未能覆盖：原因`。

## 手册整体骨架（按角色，不按页面）

1. 先弄懂这套东西怎么转（四句话讲清角色与关系）
2. 角色 A：配置与开通
3. 角色 B：日常操作
4. 角色 C（如有）：客户侧看到什么
5. 走查发现的问题（现象 → 影响 → 建议修法）
6. 上线前自检（逐条可勾选）

## 写作口吻

- 每个大功能一节，先讲「谁受影响 → 现象 → 怎么调」，再讲页面操作。
- 每一步配一张截图，图下方一句话说明「这一步看到的是什么」。
- 撞到的坑单独成节：现象 + 影响 + 建议修法。这部分往往最有用，别省。
- 明确标注走查用版本/分支，注明哪些还没进主线。

## 发布到手册站

若项目已有手册站，具体路径、端口、索引文件见项目档案；没有则输出独立单页 HTML 直接交付。通用步骤：

1. 正文写成独立单页 HTML，放 `public/manuals/<id>.html`。内联 `<style>`，图片绝对路径 `/shots/<id>/xx.png`。
2. 截图放 `public/shots/<id>/`。
3. **每个大节用 `<section id="...">` 包起来**，否则搜索只能整篇定位。
4. 在 `src/manuals/index.js` 加一条：id / title / subtitle / date / version / tag / cover / html / links / points（三条要点写「最容易踩的三个坑」）。
5. `./start.sh` 自动构建；`dev` 模式改了正文要重启 dev server 索引才重建。也可 `pnpm index` 单跑。
6. 打开 http://<本机IP>:8780/ 验证：首页卡片在、搜索关键词能命中小节、阅读页能跳到 `?s=<section>`。

## 交付自检

- [ ] 每个编号有页面概览截图 + 每个主操作一张截图
- [ ] `md5sum | uniq -c -w32` 无重复帧
- [ ] 截图里没有密码、邮箱验证码、真实客户数据
- [ ] 正文无代码、路由名、组件名、CR 编号、内部术语
- [ ] 术语与页面显示一致
- [ ] 每个大节有 `<section id>`
- [ ] 「走查发现的问题」已单列
- [ ] 首页卡片与搜索命中已验证
- [ ] 报告含：已完成编号 + 截图数、未覆盖项及原因、新登记账号（仅邮箱）、疑似缺陷、结束浏览器状态
