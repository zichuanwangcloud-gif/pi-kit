# Idea to Spec：从一句话到可开工的需求规格

```text
接收与分诊 → 问题与方案分离 → 现状取证 → 例子驱动收敛（多轮） → 切片与范围外
→ 不确定性处置（必要时转探查） → 写 spec + 八项自检 → 交接
```

细节分置于 `references/`：`elicitation.md`（每一步怎么问、例子怎么造、常见反模式）、
`spec-template.md`（产物模板、八项自检、状态判定）。

## 核心立场

需求模糊时，验收标准**不是判断出来的，是收敛出来的**。提需求的人很少能说清自己要什么，
但几乎总能对一个具体例子说「对」或「不是这样」。所以本 Skill 不追问「你要什么」，而是：

1. 先找到**问题**（谁、什么场景、损失什么），而不是接受字面上的方案；
2. 用**代码和数据中的现状**替代猜测；
3. 用**具体例子**让人挑选和否决，每一轮都让分歧更早暴露；
4. 把「不要」和「以后」显式写成**范围外**，边界就是这样画出来的；
5. 问不出来的关键未知，不硬写验收标准，转成**有时间盒的探查**。

**判断一份 spec 对不对的标准**：需求方能对每条 AC 的例子明确说是或否，且「AC 全部通过后原问题仍会出现」
的情形都已补成 AC 或列入范围外。

## 第一铁律：具体值只能来自问到的，不能来自编的

为了让每条 AC 都显得具体而凭空造出阈值、期间、文件名或列清单，是本 Skill 最危险的失控方式：
它把猜测包装成事实，且越是"看起来完整"越难被发现。

- 例子里的每个取值，必须能指向需求方原话、用户确认过的选项、或代码取证中的实测值。
- **拿不到取值时，例子列写 `待补` 并在「未决问题」登记。留空是正确答案；编一个数是错误答案，即使标了 `[推断]`。**
- `[推断]` 只用于**已有需求支撑的推导**（如「不用回头找客服」推出「失败后可自行重试」），
  不得用来掩盖凭空造出的数值、期间、格式或列清单。
- 同理，`[推断]` 不能用来"补齐"模板字段。模板里的每个字段要么填真实内容，要么写 `待补`，
  不得填「待定」「同上」这类占位符。

## 输入与参数

- 自由文本：一句话、一段场景描述、粘贴的聊天记录、粗糙的 Issue 正文（来自任何系统）
- `--out <path>`：spec 输出路径；未给时在 Step 6 提议路径并请用户确认
- `--resume <spec.md>`：在已有 spec 上继续收敛（读取其「未决问题」与「需求方确认清单」）
- `--no-code`：明确无代码上下文（新项目、非代码需求），跳过 Step 2 取证并在 spec 中声明

出现未知参数或互相冲突的参数时停止并询问，不猜。

## 安全边界

- **唯一的写操作是 spec 文档本身。** 不修改业务代码、测试、配置；不 `git add`/commit/push；不部署。
- **不写任何 Issue 系统**：不调用 Linear/Jira/GitHub Issue 等任何 tracker 的写接口，不创建或评论 Issue。
  产物是可移植的 Markdown，由用户决定粘贴到哪里。
- **不触碰主工作区的既有文件**：只新建 spec 文件；目标路径已存在且不是 `--resume` 指定的文件时停止询问，
  不覆盖。`--resume` 时只修改该 spec 文件。
- **不编造事实**：现状必须附 `文件:行` 或用户原话；拿不到证据的写 `[推断]` 或列入未决问题。
- 不把用户提供的客户名、邮箱、内网地址、凭据、生产日志原文写进 spec，用脱敏摘要代替。

## Step 0：接收与分诊

读完用户给的全部材料，先给出分诊结论，不急于提问：

```text
【分诊】
输入类型：一句话 | 场景描述 | 聊天记录 | 粗糙 Issue
需求形态：缺陷 | 新能力 | 改进 | 探索（目标本身未知）
字面诉求：<用户原话的最短复述>
它是问题还是方案：问题 | 方案（隐含问题待确认）
清晰度初判：八项自检预估通过 n/8
建议路径：直接成文（≥7/8）| 正常收敛 | 先探查
```

- 预估 ≥7/8：跳到 Step 6 直接成文，只就未通过项提问。
- 需求形态为「探索」，或连「谁受影响」都无法回答：直接按 Step 5 的探查路径处理，不硬凑 AC。
- 先读取目标仓库的 `AGENTS.md`、`CLAUDE.md`、贡献指南，了解领域术语再提问。

## Step 1：问题与方案分离

一句话需求通常是**方案**（「加个导出按钮」），背后的问题没说。产出一句不含方案的问题陈述：

```text
问题：<谁> 在 <什么场景> 下，因为 <现状>，导致 <可观察的损失>；目前靠 <绕行方式> 应付。
目标结果：G1 <问题解决后可观察的变化>；G2 ...
```

追问方法、「五个为什么」的停止条件、以及方案背后可能有多个问题时的处理，见
`references/elicitation.md` §问题与方案分离。字面方案保留为「候选方案」，**不**直接当成需求。

## Step 2：现状取证（有代码时必做）

很多模糊需求查一下现状就清楚了（「原来已经有，只是入口太深」「其实是权限没配」）。

- 定位相关的入口、生效实现与当前行为；可调用 `feature-trace`，未安装时自行完成，最低产出：
  入口、生效实现 `文件:行`、当前行为描述。
- 能低成本复现的现象（命令行、单测、本地页面）就复现，记录命令与实际输出。
- 只读：不改代码、不装依赖、不跑有副作用的命令（写库、发消息、调用外部服务）。
- 取证结果可能**改写问题本身**：发现字面诉求已被满足、或问题出在别处时，带证据回到 Step 1 与用户确认。

`--no-code` 或无仓库时跳过，并在 spec「现状」段写明「未做代码取证」。

## Step 3：例子驱动收敛（多轮）

每一轮用固定格式，**每轮最多 3 个问题，优先用例子问，不问开放式问题**：

```text
【收敛 第 N 轮】
当前理解：<问题 + 目标结果，一两句>
已确定：<上一轮定下的事>
本轮请逐条选择（要 / 不要 / 以后 / 改成…）：
  E1 <具体场景：前置 + 操作 → 系统表现>
  E2 ...
  E3 <故意放一个边界或反例>
还需回答（如有）：Q1 ...
```

- 每组例子 3–5 个，至少 1 个边界、1 个反例；造例子的方法见 `references/elicitation.md` §造例子。
- 用户选「改成…」时，按其修改重写例子并在下一轮回显，不默认自己理解对了。
- **轮数上限 5 轮。** 到上限仍有关键分歧：停止收敛，按 Step 6 以「草稿」状态成文，未决项全部列出。
- 用户不是需求方、无法代答时，不替需求方拍板：把该例子放进「需求方确认清单」，继续收敛其余部分。

## Step 4：切片与范围外

- 「要」的例子 → 候选 AC；「不要」→ 范围外（写理由）；「以后」→ 范围外并标「后续」。
- 从候选 AC 里切出**能证明目标结果达成的最小集合**，其余移入「后续」。
- 做一次**反向推演**：「如果这些 AC 全部通过，原问题在什么情况下仍会出现？」每个答案要么补成 AC，
  要么写进范围外。答「不会」必须给依据。
- 非功能约束（性能、兼容、权限、数据迁移、可观测性）逐项判断是否相关，相关的写成 AC 或约束，不相关的写一句理由。

## Step 5：不确定性处置

把剩余未知分三类，处置不同：

| 类型 | 例子 | 处置 |
|---|---|---|
| 问人能答 | 「超过 100 条时要分页吗」 | 回到 Step 3 用例子问；需求方不在场 → 需求方确认清单 |
| 查证能答 | 「现在接口有没有返回这个字段」 | 回到 Step 2 取证 |
| 只有试了才知道 | 「用户会不会用这个功能」「这个第三方接口延迟多少」 | **转探查**：不写功能 AC，改写为探查 spec |

探查 spec 的验收标准是「要回答什么问题」而不是「要交付什么功能」：列出待回答的问题、时间盒、
产出物（结论文档/原型/数据）、以及每种结论对应的下一步。模板见 `references/spec-template.md` §探查型 spec。

## Step 6：写 spec 与八项自检

1. 按 `references/spec-template.md` 的模板写成 Markdown。每条 AC 必须：EARS 句式、一个断言点、
   对应一个目标结果、至少一个具体例子。
2. 逐项写出八项自检的通过/未通过，**缺口数 = 未通过项数**，不得凭感觉给数。
3. 按模板的状态判定给出 spec 状态：`可开工` / `待需求方确认` / `草稿` / `探查`。
4. 输出路径：用 `--out`；未给时提议一个路径（优先沿用仓库既有的 spec/需求文档目录，没有则提议
   `specs/<yyyy-mm-dd>-<slug>.md`）并请用户确认。写入前确认目标文件不存在（`--resume` 除外）。
5. 写完后在对话里回显：spec 路径、状态、八项自检结论、未决问题数、需求方确认清单条数。

## Step 7：交接

- `可开工`：告诉用户可以把 spec 粘贴进任何 Issue 系统，或直接作为开发输入。
  若使用 `linear-to-pr`，把 spec 正文放进 Issue 描述即可——spec 的段落与其理解卡一一对应，八项自检口径相同。
- `待需求方确认`：给出可直接转发的「需求方确认清单」文本；拿到回复后用 `--resume` 继续。
- `草稿`：列出阻塞成文的分歧，建议需要谁参与下一轮。
- `探查`：给出探查完成后回到本 Skill 的方式（`--resume` 并附上探查结论）。

## 立即停止并询问

- 目标路径已存在且不是 `--resume` 的文件；或 `--resume` 的文件不是本 Skill 产出的 spec 结构。
- 用户材料里有互相矛盾的说法且无法判断哪个是最新口径。
- 取证发现字面诉求已被满足，或问题实际出在另一个系统/团队的范围内。
- 收敛中出现明显超出原问题的新范围（应拆成另一份 spec）。
- 需要读取的材料涉及凭据或敏感数据原文。

**不要重复询问已确定的事项**；已确定内容只在「当前理解 / 已确定」里回显，不再作为问题出现。
