# 收敛技法：怎么问、怎么造例子

把模糊需求收敛成可验收需求的提问方法。目标是每一轮都让分歧更早暴露，而不是收集更多描述。

## 问题与方案分离

把字面诉求当成「候选方案」，向下追问它要解决什么：

| 追问 | 目的 |
|---|---|
| 「没有它的时候，现在是怎么做的？」 | 找到绕行方式，绕行的成本就是损失 |
| 「最近一次遇到这个问题是什么时候、什么情况？」 | 把抽象诉求落到一个真实事件 |
| 「谁会第一个发现它做好了？他会看到什么变化？」 | 得到可观察的目标结果 |
| 「如果只能做一半，先要哪一半？」 | 暴露优先级与最小切片 |

**「五个为什么」的停止条件**：追到出现**可观察的损失**（时间、金钱、错误、流失、合规风险）就停，
不要追到「提升用户体验」「业务需要」这类不可验证的抽象层。

一个方案背后可能有多个问题（「加导出」可能是要对账、要备份、要给老板看报表）。出现这种情况时，
把几个问题并列给用户选，每个问题对应的最小方案可能完全不同；不要合并成一个「通用」方案。

## 造例子

一个好例子 = **具体前置 + 具体操作 → 具体可观察表现**，全部用真实取值：

```text
差：用户导出数据时系统应正确处理。
好：账号下有 12,000 条订单，用户在订单页点「导出 CSV」→ 30 秒内收到下载，文件含 12,000 行和表头。
```

每组 3–5 个例子，按下面的来源组合，至少覆盖一个边界和一个反例：

- **典型路径**：最常见的那一种用法，取一个真实规模的数值。
- **输入边界**：空、1 条、上限、超过上限、非法格式。
- **身份与权限**：不同角色、跨租户、未登录、权限被收回的中途。
- **时间与并发**：重复点击、两人同时操作、操作到一半失败、重试。
- **旧数据与兼容**：历史数据缺字段、旧版本客户端、迁移中途。
- **反例**：一个「看起来相关但不应该被这个需求改变」的行为（系统不应当……）。

例子要**故意让人能否决**：给出一个你不确定的取值（「超过 1 万条改为异步邮件发送」），
比问「大量数据怎么办」更快得到答案。

## 好问题与坏问题

| 坏问题 | 为什么坏 | 改成 |
|---|---|---|
| 「你希望这个功能是什么样的？」 | 开放式，对方只能复述原话 | 给 3 个例子让对方选 |
| 「需要考虑性能吗？」 | 对方一定说需要 | 「1 万条时 30 秒内完成可以接受吗？还是要 5 秒？」 |
| 「还有别的需求吗？」 | 引出范围蔓延 | 「下面这两个场景这次先不做，可以吗？」 |
| 一次问 8 个问题 | 对方只回答前两个 | 每轮 ≤3 个，按阻塞程度排序 |
| 「这样理解对吗？」+ 一大段复述 | 对方会扫一眼说对 | 把复述拆成例子，逐条选 |

## 需求方不在场

和 Skill 对话的常常是开发者，不是提需求的人。此时：

- 开发者能凭已有材料或常识回答的，正常收敛，但在 spec 里标注来源为「开发者判断」。
- 涉及业务取舍（要不要、优先级、可接受的阈值）的，不替需求方拍板，放进「需求方确认清单」。
- 清单写成**可直接转发**的形式：每条是一个具体例子 + 选项（要 / 不要 / 以后 / 改成…），
  附一句为什么需要确认，不附内部术语和代码路径。
- spec 状态在清单清空之前只能是 `待需求方确认`，不得标为 `可开工`。

## 常见反模式

- **把方案当需求**：直接为「加个按钮」写 AC，结果按钮做出来了，问题没解决。
- **用形容词写 AC**：「快速」「友好」「正确」「合理」——没有可判定的阈值就不是 AC。
- **只有正向例子**：没有边界和反例，最贵的缺陷都藏在这里。
- **没有范围外**：边界不写出来就等于没有边界，评审时每个人脑中的范围都不一样。
- **一轮问完**：模糊需求不可能一次问清，强行一次问完只会得到敷衍的答案。
- **用户沉默即同意**：用户没回答的例子仍是未决，不得按自己的猜测补进 AC。
