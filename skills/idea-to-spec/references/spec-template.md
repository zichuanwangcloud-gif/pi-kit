## 功能型 spec

```markdown
# <一句话标题：问题导向，而不是方案导向>

> 状态：可开工 | 待需求方确认 | 草稿　｜　更新于 <yyyy-mm-dd>　｜　收敛轮数 <n>

## 问题
<谁> 在 <什么场景> 下，因为 <现状>，导致 <可观察的损失>；目前靠 <绕行方式> 应付。[来源]

## 目标结果
- G1 <问题解决后可观察的变化> [来源]

## 现状
- 入口：... `文件:行`
- 当前行为：... `文件:行`（或复现命令 + 实际输出）
- 未做代码取证时写明：「未做代码取证（原因）」

## 候选方案
- 采用：... 理由：...
- 放弃：... 理由：...

## 验收标准
| # | EARS 句式 | 支撑 | 例子（前置/输入 → 期望输出） | 来源 |
|---|---|---|---|---|
| AC1 | 当 <事件> 时，系统应当 <行为> | G1 | <真实取值> → <可观察输出> | 用户确认 / 需求方确认 / 开发者判断 / [推断] |
| AC2 | 如果 <异常/边界条件>，那么系统应当 <行为> | G1 | ... | ... |

## 约束（非功能）
- 性能 / 兼容 / 权限 / 数据迁移 / 可观测性：<约束> 或「不相关：理由」

## 范围外
- <场景>：不做 | 后续 — 理由

## 反向推演

- AC 全过后原问题仍可能出现的情形：... → 已补 ACn | 列入范围外

## 未决问题
- Q1 ... — 阻塞哪条 AC — 需要谁回答

## 需求方确认清单

## 有效性信号
- 上线后看什么判断问题解决了：<指标或现象>，在 <哪里> 看，预期 <变化>

|---|---|---|---|
| ① | ... | 通过/未通过 | ... |
```

## 探查型 spec

目标本身未知、或关键未知「只有试了才知道」时使用。验收的是**问题被回答**，不是功能被交付：

```markdown
# 探查：<要弄清的问题>

> 状态：探查　｜　时间盒 <例如 2 人日>　｜　更新于 <yyyy-mm-dd>

## 背景问题
<同功能型 spec 的问题陈述，允许部分为 [推断]>

## 待回答的问题
| # | 问题 | 回答方式（原型/数据查询/用户访谈/压测） | 判定标准 |
|---|---|---|---|
| Q1 | 第三方接口 P95 延迟是多少？ | 在测试环境压测 1,000 次 | 拿到 P50/P95/P99 数值 |

## 产出物
- 结论文档 / 原型（一次性，不进主线）/ 数据

## 结论 → 下一步
- 若 Q1 < 200ms：按同步方案写功能型 spec
- 若 Q1 ≥ 200ms：按异步方案写功能型 spec，或放弃

## 范围外
- 探查期间不做生产级实现、不上线

## 需求方确认清单
<!-- 与功能型 spec 同义：探查期间仍需业务方拍板的事 -->

## 八项自检
<!-- 同样要写，逐项通过/未通过 + 缺口数。探查型只是换掉验收标准形态，不豁免自检 -->
```

**探查型 spec 的必填段落**：`背景问题`、`待回答的问题`、`产出物`、`结论 → 下一步`、`范围外`、
`需求方确认清单`、`八项自检`。其中：

- **时间盒必填**（写进文档头）——没有时间盒的探查是开放式工作，不允许开工。
- **每个问题必须有「回答方式」和「判定标准」**——否则「回答完了」无法判定。
- **`结论 → 下一步` 必填**——探查的价值在于结论能推动决策，没有映射的探查没有产出。

> 实测教训：被测方把探查模板的段落整段省略（只留「待回答的问题」），理由是「验收标准/反向推演不适用」。
> 适用与否由本模板规定，不由执行者临时判断：探查型**换掉**验收标准形态，但**不豁免**自检与范围外。

## 两种实测高频幻觉，写 spec 时逐条自查

### 1. 确认外溢

**形态**：你向需求方提了一整段（包含自己的猜测），对方只认了其中一部分，
你把这份「认」扩大到整段，连自己猜的部分也变成「用户确认」。

实测案例：提问里写了「导出入口埋得很深，导致他们转而向客服/研发要数据，目前靠人工从后台或数据库直取应付」，
需求方只回「这个我认，按这个方向来」（认的是"入口可见性"这个方向），
spec 却把整段标成「用户第 1 轮确认」——**绕行方式是自己编的，从未被确认**。

**自查**：每条标「用户确认」的内容，逐字回到对话里看——**对方确认的是哪一句？**
只把那一句标为确认，其余标 `[推断]` 或写进未决。一段话里只有一部分被确认时，**必须拆开标**。

### 2. 范围外扩张

**形态**：需求方顺口一说「那些以后再说」，你据此把一整类东西写成「范围外·不做」，
而需求方原话覆盖的只是里面一项。

实测案例：需求方说「验证码、人工解封、发通知那些以后再说」，
spec 的范围外就此写死了这三项，还在其中混入了自己推断的「手机号/地址脱敏写法」
（仓库里根本没有这个字段）。

**自查**：范围外每一条都要能指回具体原话；指不回去的，要么删掉，要么标注为
「开发者建议排除，待确认」，不得列入已定范围外。

## AC 写法

- **EARS 句式**：`[当<事件>时 / 如果<条件>那么 / 在<状态>期间]，系统应当<行为>`；
  负向用「系统不应当<行为>」。写不成 EARS 即视为不可验收。
- **一条一个断言点**：出现「并且」「同时」或两个以上动词短语就拆分。
- **阈值必须是数**：不写「快速」「大量」「友好」，写「30 秒内」「12,000 条」「错误提示含字段名」。
- **例子只能来自被问到的值，不得自己造值**。这是本 Skill 最重要的一条反幻觉规则：
  为了让每条 AC 都显得具体而凭空编出阈值、期间、格式或列名，等于把猜测伪装成事实——
  评测中已实测发生（把 30 分钟基线除以 6 造出「≤5 分钟」的阈值）。
  - 例子里的每个取值都必须能指向：需求方明确说过的原话、用户确认过的选项、或代码取证中的实测值。
  - **拿不到取值时，例子列写 `待补` 并在「未决问题」登记，不许填一个看起来合理的数。**
    留空是正确答案；编一个数是错误答案，即使标了 `[推断]`。
  - `[推断]` 只能用于**已经由需求支撑的推导**（例如「不用回头找客服」推出「失败后可自行重试」），
    不能用于掩盖凭空造出的数值、期间、文件名或列清单。
- **例子用真实取值**：例子就是测试用例的雏形，开发阶段可直接转成验收测试。
- **来源要诚实**：只有用户或需求方明确选过的例子才能标「用户确认」「需求方确认」。
  来源写「开发者判断」时必须能指出判断依据；写不出依据的，按上面第 1 条写成 `待补`。

## 八项自检

逐项写出通过/未通过，**缺口数 = 未通过项数**。
写缺口数时**逐行数一遍**未通过的行，不要凭感觉给数——评测中实测出现「写了 2、实际 1」的自相矛盾。
若某行既非通过也非未通过，不得写「部分通过」：它必须归入通过或未通过之一。

| # | 自检项 |
|---|---|
| ① | 期望明确（不只有现象） |
| ② | 用户提供的全部材料已读完，现状已取证或已声明未取证 |
| ③ | 材料中的冲突已解决 |
| ④ | 有可验证验收标准（EARS 句式成立；例子列要么有真实取值，要么诚实写 `待补`，无凭空造值） |
| ⑤ | 已定位唯一落点，或明确为新增能力并说明放在哪里 |
| ⑥ | 已知触发条件 |
| ⑦ | 追溯链完整：问题与目标结果有非推断来源，无孤儿 AC，每个目标结果至少被一条 AC 覆盖 |
| ⑧ | 至少一条负向/边界 AC（或写明不存在的理由），且反向推演的每个答案都已补 AC 或列入范围外 |

## 状态判定

| 状态 | 条件 |
|---|---|
| `可开工` | 缺口数 0；需求方确认清单为空（或用户本人就是需求方）；无未决问题阻塞 AC |
| `待需求方确认` | 缺口仅来自需求方确认清单中尚未回复的条目 |
| `草稿` | 达到 5 轮上限仍有关键分歧，或缺口 ≥1 且不属于上一行 |
| `探查` | 使用探查型模板 |

状态只能按上表判定，不得因为「基本清楚了」手动升级。
