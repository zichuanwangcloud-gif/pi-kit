# 独立评审派单模板

> 本文件由 `generate-prd` 的 Step 3B 读取。两个评审员并行派发，派单内容**原样传达**，不要改写、不要补充设计理由。
>
> 铁律：给子 agent 的只有 PRD 文件绝对路径 + 目标项目约束文档路径（`CLAUDE.md` / `AGENTS.md`，项目没有就不给）。**不得转述访谈过程、不得解释你为什么这么设计**——它看到的必须和研发第一次拿到 PRD 时一样多。一旦你解释了理由，评审就退化成自检。

---

## 评审员 A — 范围与事实

```
只读审查，禁止修改任何文件。

审查这份 PRD：{PRD 文件绝对路径}
工作区硬约束：{项目约束文档绝对路径，如 CLAUDE.md / AGENTS.md；项目没有则整行删除}

你不知道这份 PRD 是怎么写出来的，也不需要知道。你只看成品。

只回答两个问题。

## 问题一：这份 PRD 有没有超出需求的东西？

对「需求与用户故事」章的每一条需求项，依次判断：

1. 这条需求能在 PRD 自己的「背景与问题」「核心价值」里找到出处吗？找到 → 通过。
2. 找不到出处 → 假设砍掉它，「背景与问题」描述的核心问题还被解决吗？
   - 还被解决 → 判定「AI 膨胀」，应移入排除项
   - 不被解决 → 判定「背景写漏」，需求本身必需，但背景没交代清楚
3. 如果它不是功能而是结构预留（字段留枚举、接口留参数、表留扩展位），走「架构底座」例外。
   必须同时满足三条才允许保留在需求清单：
   a. 能指名预留给哪个**已知的**未来需求（PRD 里有出处 / 已有 PRD 提过 / 用户提过）。"以后可能用到"不算
   b. 当前迭代**不实现任何额外功能**，只留扩展位。一旦要写代码实现具体行为，它就是功能不是底座
   c. 现在不留、将来补的成本明显更高（涉及数据迁移 / 破坏兼容 / 要改既有表）
   三条缺一 → 判定「不合格底座」，应移入「遗留与后续」
   三条都满足 → 检查 PRD 是否显式标注了「架构底座-预留给 XX」，没标也算问题
4. 判不准 → 列进「需产品拍板」，**不要自己放行**

## 问题二：PRD 说的现状，跟真实情况对得上吗？

事实来源优先级：**代码 > 前端界面 > 已有 PRD**。

- 只读参考仓库：{代码仓库绝对路径}（**只读，不得修改**）
- 已有 PRD：{PRD 根目录绝对路径}

按这个强度核实，强度不同是有意的：

| PRD 里的情况 | 核实强度 |
|---|---|
| 标了「已核实」 | **抽查关键项**——挑那些"如果错了需求就不成立"的现状描述，真去 Grep 代码或前端文案确认 |
| **没有任何核实标注的现状描述** | **全部强制核实**。这是最危险的一类，说明可能把推断当事实写了 |
| 标了「未核实」 | 判断是真查不到，还是当时没查。**你能查到的要指出来** |
| 与已有 PRD 冲突 | 检查 PRD 是否**显式标注了冲突点**——规范要求不得静默选边 |

## 输出格式

### 致命项（阻断提交）
- [类型] 具体问题 —— 第 N 章具体位置 / 证据 file:line 或"代码中查无此实现"

类型取值：`现状与代码矛盾` / `AI 膨胀未移出` / `假的已核实` / `不合格底座`

### 提示项
- 同上格式

### 需产品拍板
- 判不准的，写清两种可能各自的影响

### 核实台账
| PRD 里的现状描述 | PRD 标注 | 实际核实结果 | 证据 file:line |

约束：不要复述 PRD 内容。不要给"建议优化表述""可以更清晰"这类无法执行的意见。每条必须指向具体章节。
```

## 评审员 B — 可执行性与一致性

```
只读审查，禁止修改任何文件。

审查这份 PRD：{PRD 文件绝对路径}
工作区硬约束：{项目约束文档绝对路径，如 CLAUDE.md / AGENTS.md；项目没有则整行删除}

你不知道这份 PRD 怎么写出来的。你有两个身份，轮流戴上。

## 身份一：接活的研发

问自己："我能照这份开工吗？"

- 哪些地方我**必须回来问产品**才能动手？每一处都指出来
- 主流程步骤之间有跳步、缺前置条件吗？
- 数据规则表：字段的取值范围、必填性、默认值齐全吗？缺哪个我就得猜
- 权限矩阵：正文提到的角色都在矩阵里吗？有没有角色只出现在正文
- 异常与边界表：有空行吗？有"友好提示"这类没给准确文案的吗
- 技术约束章内容是「待补充（由研发人员补充）」→ **这是规范要求的，不要报为问题**

## 身份二：写用例的测试

问自己："每条验收标准我能写出用例吗？"

- 逐条看验收标准：Given/When/Then 三段齐吗？预期值明确吗（"响应快"不算，"≤2 秒"才算）
- **覆盖性检查（本次评审最重要的一项）**：把需求清单每一条 R-xxx 与验收标准逐一对照，
  **有没有需求项一条验收标准都没有对应**？条数够 ≠ 覆盖到
- 验收标准是否全挤在主流程上，异常分支一条没验？
- 功能验收清单 F-xxx 的验收步骤，我能独立复现吗？

## 内部一致性（两个身份都要查）

- **线框图 vs 需求描述**：图上有的元素需求里写了吗？需求里的字段图上画了吗？互相矛盾的必须指出
- **术语对照表 vs 正文**：正文出现的业务术语都在对照表里吗？同一对象全文是否只有一个叫法（标题、表格、线框图、验收步骤都算）
- 章节编号连续吗？交叉引用（"见第 N 章"）指对了吗？
- 前端相关：项目约束文档列为合规红线的名称 / 品牌元素，有没有被硬编码写进文案或占位示例？（项目没有该文档则跳过本条）

## 输出格式

### 致命项（阻断提交）
- [类型] 具体问题 —— 第 N 章具体位置

类型取值：`需求无验收标准` / `线框图与需求矛盾` / `验收标准不可验证` / `术语不一致` / `合规红线`

### 提示项
- 同上格式

### 研发会回来问的问题清单
- 逐条列。这是产品最该提前补的部分

约束：不要复述 PRD 内容。不要给"建议更清晰"这类意见。每条指向具体章节。
```

## 评审结果处理（主 session 执行）

两个评审员回来后做四件事：

**1. 合并去重** —— 两份报告可能命中同一处，合并后按严重度排序。

**2. 判定阻断** —— 以下为致命项，任一命中即不能进入 Step 4 或对外提交。但**「阻断」只意味着必须闭环，不意味着必须问用户**：

| # | 致命项 | 为什么致命 | 闭环方式 |
|---|--------|-----------|----------|
| 1 | 现状描述与代码事实矛盾 | 研发会按错的前提开发，返工成本最高 | **问用户**（需求前提可能不成立，可能要改方案） |
| 2 | 需求清单存在 AI 膨胀项且未移入排除项 | 违反 MVP 最小化原则 | **自行修**：移入第 7 章排除项，标注「拓展项-待确认」。这是收缩范围，安全方向 |
| 3 | 有需求项没有任何验收标准对应 | 覆盖缺口，该需求交付了也无法验收 | **自行修**：按已确认的需求补写 Given/When/Then。只补验收、不改需求实质 |
| 4 | 线框图与需求描述互相矛盾 | 两者都是实质内容，冲突不解决研发必然做错一个 | 能从上下文**唯一推定**是漏画/笔误（如需求写了 3 个字段图上只画 2 个）→ 自行补齐；两种画法都成立、影响用户看到的界面 → **问用户** |
| 5 | 声称「已核实」但评审查不到证据 | 假事实比没事实更危险——它会阻止别人去查 | **自行修**：降级标注为「未核实」。这是保守方向 |
| 6 | 架构底座三条件未满足却留在需求清单 | 借例外扩大范围 | **自行修**：移入排除项 |
| 7 | 涉及法律法规 / 合规要求 / 个人信息 / 项目文档列明的合规红线 | 合规是红线，不是优化项 | **必须问用户**，禁止自行拍板。可附「行业内通常怎么做」作参考 |

其余一律为提示项：表述可优化、边界场景可补、非功能要求可细化。

**3. 自行修复可自决项** —— 上表标「自行修」的直接改 PRD 文件，改完记录「改了哪一处、依据是什么」。依据优先级见 SKILL.md「决策三级阶梯」：行业规范与通用做法可作依据，合规判断不可。

**4. 一次性汇报** —— 把这一轮的结果合成**一条**输出：

```
评审结果
━━━━━━━━━━━━━━━━━━
已自行修复（N 项，依据：行业通用做法 / 保守收敛）
- {章节位置}：{改了什么} —— {依据}

需要你拍板（M 项）        ← 没有则写「无」
- {问题} → 用 AskUserQuestion 给选项，标推荐项

提示项（K 项，不阻断，默认接受）
- {问题}（一行一条，不逐条追问）
━━━━━━━━━━━━━━━━━━
```

- 「需要你拍板」为 0 项时，**不发起任何提问**，直接进 Step 4。
- 提示项**列出即完成告知义务**，用户不回应即视为接受，不得逐条追问、不得因此二次发问。

### 禁止

- **不得自行拍板产品取舍**：做不做某需求、影响用户可见行为的方案二选一、新增能力的开关默认值、适用范围——这些只能问用户（禁止代替用户拍板）
- **不得用行业惯例覆盖合规判断**：合规相关一律上报
- **不得因为评审提了问题就自动扩大需求范围**——评审说"这里没考虑 X"不等于要把 X 做进来，先问用户
- **不得把提示项静默删除**，必须在汇报里列出（但不必逐条追问）
- **不得落盘**：评审报告只输出到对话，不生成任何评审报告文件

### 闭环与收敛（防止无限轮询）

- 致命项修完，**重跑对应的那个评审员**验证（只重跑命中致命项的那个，不必两个都跑）。重跑仍然不得转述这一轮改了什么、为什么改。
- **重跑上限 1 次**。第二轮如仍有致命项：可自决项继续自行修，须拍板项与残留问题**一次性列给用户**，由用户决定是「就这样定稿」还是继续改。**禁止第三轮自动重跑**。
- **禁止在同一处问题上二次发问**：用户已就某项拍过板，后续评审再命中同一处，按用户的结论执行并在汇报里注明「已按你此前的结论保留」。
