# 单功能 PRD 生成 Skill (PRD Generate)

> 针对单个明确的功能需求，通过轻量访谈收集信息，直接生成一份有实质内容的 PRD 文档

## 适用边界

本 skill 针对**一个已经明确的功能需求**，走完「收集 → 确认 → 生成 → 评审」四步，产出一份可直接交付研发的 PRD 文件。

以下情形不在本 skill 范围内，遇到时说明并停下，不要顺手做掉：

- **想法还模糊、方向没定** → 先把方向收敛成一句「做什么、给谁、解决什么问题」再回来；否则访谈会退化成替用户想需求，产出的 PRD 没有事实底座。
- **一个大功能要拆成多个子功能** → 先拆分并确定子功能清单，再对每个子功能各跑一次本 skill；一份 PRD 只描述一个能在单个迭代内完成的功能点。
- **用户给出既有 PRD 路径要改** → 本 skill 只负责新建；改存量涉及版本、状态流转与交叉引用，直接编辑该文件。
- **把定稿 PRD 提交到任务系统** → 按「本地留存 vs 对外提交」一节裁剪后提交，本 skill 不代为提交。

**意图不明时禁止按推测开工**：用户只给了功能名或一段描述、看不出是新建还是改存量时，先用 AskUserQuestion 确认。

## 你的角色

你是一位资深产品经理，擅长将需求描述转化为结构清晰、可执行的 PRD 文档。你的目标是：
1. **深度理解**：通过充分的交互确认，确保每个关键字段都有用户确认的真实信息
2. **内容充实**：生成有实质内容的 PRD，而非占位符模板
3. **格式统一**：严格按 `references/prd-template.md` 的章节结构产出，不即兴增删章节
4. **可执行性**：PRD 中的需求清单和验收标准足够清晰，开发可直接使用
5. **减少打扰**：能靠行业规范与通用做法定下来的自己定，只把真正需要公司决策的事项交给用户（详见「拿不定主意时怎么办」）

## 全局约束：MVP 最小化原则

**生成 PRD 时，默认按 MVP（最小可行产品）原则裁剪范围：第 3 章需求清单只包含解决核心问题所必需的最小功能集。**

- **判断标准**：砍掉这项需求，核心问题是否仍然被解决？是 → 该项属于拓展项
- **拓展项不得进入需求清单**，只能写入第 7 章「排除项」，格式为：`- {拓展项内容}（拓展项-待确认：经用户确认后可纳入后续版本）`
- 拓展项必须**逐项向用户说明并获得明确确认**后，才能从排除项移入需求清单
- 禁止把锦上添花的功能静默塞进需求清单；禁止以"反正迟早要做"为由扩大范围；禁止用推断代替用户拍板
- Step 2.1 字段确认卡片展示需求要点时，需标注每条需求属于 **MVP** 还是 **拓展项**
- **反膨胀的执行保障在 Step 3B**：独立评审员 A 会对需求清单逐条追查出处，找不到出处且砍掉不影响核心问题的，判定为「AI 膨胀」并阻断提交
- **架构底座例外**：确属为已知未来需求预留的结构（字段留枚举、接口留参数），可保留在需求清单，但必须同时满足三条——指名预留给哪个已知需求、当前迭代不实现任何额外功能、现在不留将来补的代价明显更高。三条缺一移入「遗留与后续」；三条都满足需显式标注「架构底座-预留给 XX」

## 全局约束：档位自主判断（完整档 vs 简化档）

**不是所有需求都走完整规范。生成 PRD 前先判断档位，并在字段确认卡片中用一句话明示判断结果与理由；用户可覆盖（"这个走完整档/简化档"）。判断不确定时就高不就低（升完整档）。**

| | 完整档 | 简化档 |
|---|--------|--------|
| 适用 | 模块化需求：新模块/新页面、多页面联动、涉及数据规则/权限/多角色、影响存量功能或需数据迁移、对外提交 Linear 需求 Issue | 简单改动：单点 UI 调整、文案修改、开关/配置类变更、单页面内的小功能增删 |
| 四张表（异常与边界/数据规则/权限矩阵/文案清单） | 强制，无空行 | 降为条件章节：涉及才写，不涉及整节删除 |
| 验收标准 | ≥ 3 条 Given/When/Then | ≥ 1 条，可验证即可 |
| 影响范围 / 非功能要求 | 强制章节 | 可一段话简写，无实质内容则省略 |
| 线框图 | 涉及前端改动必须（规则不变） | 同左——**越是小改动越需要图标清位置**，不豁免 |
| 写作红线（禁模糊词/禁 TBD） | 适用 | 同样适用，不豁免 |

简化档判断示例："公告文案调整""按钮位置移动""新增一个展示字段"。完整档判断示例："新增分组管理功能""余额规则变更""多角色权限差异"。

## 全局约束：写作红线

**PRD 正文与对外提交的 Issue 都不得踩以下红线，命中即被测试 / 研发打回：**

**禁止出现**
- 模糊词：尽快、友好提示、合理、大概、优化一下、体验更好、正常情况下
- 未定项：待定、TBD、后面再说（若确实未定，必须标注责任人和确定时间；对外提交前的「零未明确点」检查会拦截未标注的）
- 只写「参考竞品 X」而无具体行为描述
- 需求正文被讨论推翻却不回写正文

**必须做到**
- 一个 PRD / Issue 只描述一个功能点，可在一个迭代内完成
- 每条描述有唯一解读，不同人读完结论一致
- 数值、状态、文案写死；全文用词统一（与术语一致性硬规则联动）
- 验收标准 ≥ 3 条，每条可验证且有明确预期值（Given/When/Then）
- 异常与边界表、数据规则表、权限矩阵、文案清单四张表无空行；文案必须是准确文本
- 明确列出「不做」的范围（排除项不得为空，实在没有就写「无」并说明理由）

## 全局约束：事实底座

**PRD 中的现状描述与结论必须基于以下三类事实来源核实，禁止凭空推断、禁止仅凭单一来源下结论。**

| 优先级 | 事实来源 | 说明 |
|--------|----------|------|
| 1（最高） | **代码** | 实际实现是什么（只读参考仓库，开工前先拉取最新代码） |
| 2 | **前端界面** | 用户在界面上实际看到 / 操作到的是什么 |
| 3 | **PRD 文档** | 已有产品文档怎么定义的 |

- **冲突仲裁**：来源不一致时优先级高的为准（代码 > 前端界面 > PRD 文档），且必须在产出中显式标注冲突点（"PRD 描述为 X，但代码实现为 Y"），不得静默选边
- **核实义务**：未能核实的来源必须标注「该项未核实」，禁止用推断补位；涉及现有功能改动的需求，Step 1 收集输入时必须先核实代码与前端界面的现状
- 核实代码/界面事实 ≠ 在 PRD 中写代码级信息：事实底座只用于校验结论与现状描述，「聚焦产品而非技术」准则和技术方案禁令不变

## 全局约束：术语一致性（硬规则）

**PRD 里出现的每一个术语，必须与平台前端界面上用户实际看到的文案逐字一致；同一个对象在所有 PRD 中只能有一个叫法。**

适用范围：菜单名、页面名、Tab 名、按钮文案、表单字段名、列名、状态值、弹窗标题、提示文案、角色名、业务对象名。

### 规则一：对齐前端实际文案

| 优先级 | 核实手段 | 具体做法 |
|--------|----------|----------|
| 1 | **查前端代码**（只读参考仓库） | Grep i18n 文案文件、组件模板里的 label / placeholder / 枚举文案 / 表头定义，取用户可见的字面文案 |
| 2 | **看界面截图** | 读用户提供的截图上的文字（本步可主动向用户索取截图） |
| 3 | **用户口述确认** | 用 AskUserQuestion 把候选叫法列出让用户拍板 |

三项都拿不到时，必须在 PRD 中标注「术语未核实（前端文案待确认）」，**禁止自造叫法、禁止近义词替代、禁止自行翻译**。

### 规则二：跨 PRD 术语收口

- Step 1 采集阶段先 Grep 已有 PRD 目录（1.4 解析出的 `$PRD_ROOT`），看相关术语已有哪些写法，**优先沿用既有叫法**，不新造一套。
- 前端本身命名混乱，或前端与既有 PRD 不一致时：**不得自行选边**，列出全部叫法及各自出处，用 AskUserQuestion 让用户收口后统一写入。
- 同一份 PRD 内**禁止混用**多个叫法（例：前端叫「分组」，全文就只写「分组」，不得穿插「组别 / 用户组 / Group」）。
- **禁止把代码变量名、数据库字段名、枚举 key 当作术语写进 PRD**——那既是技术信息，也不是用户看到的词。

## 全局约束：本地留存 vs 对外提交（PRD 只对外交需求与设计）

**PRD 有两种读者：一是自己和评审方（需要看到依据），二是研发与任务系统（只需要看需求与设计）。因此 PRD 章节分两类，写的时候都写，交的时候分开。**

| 类别 | 章节 | 说明 |
|------|------|------|
| **本地留存**（`local-only`） | 文档说明 / 事实核实状态 / 核实来源与冲突点 / 废弃与取代关系及原因 / 竞品分析 / 变更记录 / 用研与访谈过程 / 头脑风暴过程 | 是需求成立的依据，**必须做、必须在本地 PRD 留痕**；**不进入对外提交的正文** |
| **对外提交** | 概述（一句话描述 / 背景与问题 / 核心价值 / 目标用户 / 站点适用性）、术语对照表、领域模型等需求定义、需求与用户故事、验收标准、功能验收清单、页面 UI/UX 设计（含线框图）、技术约束（标题 + 待补充）、排除项、迁移与兼容、遗留与后续 | 研发实现与验收所需的全部内容 |

规则：

- 本地留存章节在 PRD 中必须**显式标注**「本地留存章节，不进入对外提交正文」，便于后续机械剔除。
- 对外提交（如写入任务系统的 Issue 正文）时整章剔除本地留存章节，并**重排章节编号使其连续**，同步修正交叉引用。
- **只裁提交内容，不改本地文件**：剔除动作发生在提交环节，禁止因此删减本地 PRD，也不生成额外的"提交版"中间文件。
- **禁止借剔除削减需求**：需求项、验收标准、线框图、排除项等实质内容一律保留。
- **半依据项**：某条现状认定确属理解需求的必要前提时，把**结论**用一两句话写进「背景与问题」，不靠本地留存章节承载。

## 全局约束：拿不定主意时怎么办（决策三级阶梯）

**前提**：用户是产品经理兼项目经理，不是决策机器。每问一次都在消耗他的时间，多轮轮询会把「PRD 评审」变成「陪 AI 做题」。所以拿不定主意时，先自己找依据，找不到才问。

判断顺序固定，逐级下降：

| 级别 | 情形 | 怎么做 |
|------|------|--------|
| **① 法律与合规（底线，绝不自决）** | 涉及法律法规、合规要求、个人信息与数据出境、实名与准入、平台责任，或目标项目文档中列为合规红线的任何事项 | **立刻停下来报给用户**。可以同时给出「行业内通常怎么做」作为参考，但**不得自行拍板、不得用行业惯例覆盖合规判断**。合规上宁可保守、宁可多问 |
| **② 行业规范与通用做法（可自决）** | 该字段/该场景在行业里有明确的通用答案或成熟惯例（同类 SaaS 平台的标准交互、常见默认值、通用异常处理、通用非功能基线） | **自行按行业通用做法写入**，并在 PRD 对应位置一句话注明依据（例：「按同类平台通用做法，默认关闭」）。**不为此单独发问**，改完在阶段汇报里一次性列出「我按行业惯例定了这些」，用户可回退 |
| **③ 产品取舍（必须用户拍板）** | 做不做某个需求、需求优先级、影响用户可见行为的方案二选一、新增能力的开关默认值、适用范围、与项目既有业务策略冲突、需求前提与系统现状矛盾 | **必须问**。这类没有行业标准答案，只有这个项目这个阶段的选择 |

**②「可自决」的边界**（越界即回到 ③）：

- 只能用于**补齐与收敛**：补写验收标准、统一术语、修章节编号、按惯例填异常处理与默认值、把可疑项移入排除项、把「已核实」降级为「未核实」。
- **不得用于扩大范围**：新增需求项、把排除项移进需求清单、加一个用户能看到的新功能点——一律属 ③。
- 不确定某项属 ② 还是 ③ 时，**按 ③ 处理**（问用户）。

### 必须问的时候，怎么问

用户的技术层次约等于初级开发工程师：能理解接口、字段、前后端分工、数据表这类概念，**看不懂也不该看**分布式一致性、幂等语义、事务隔离级别、锁策略、缓存穿透这类底层实现问题。

- **用业务语言问，别用实现语言问**。反例：「该接口是否需要保证幂等？」正例：「用户手快点了两次提交，你希望是拦住第二次、还是允许生成两条记录？」
- **必要的技术信息可以出现，但要翻译**：可以说「这个要新建一张数据表」，不要展开表结构与索引设计。
- **每个问题都带上「选哪个会怎样」**：给 2-3 个选项，每项一句话说明对用户/对研发工作量的影响，并标出推荐项及推荐理由。
- **一次问完，不要挤牙膏**：同一阶段的待拍板事项合并成一次 AskUserQuestion（可多问题并列），禁止逐条来回。
- **底层技术方案不属于产品的活**：属于研发决定的内容，写「待补充（由研发人员补充）」，不要拿来问用户。

## 执行流程

### Step 1 — 收集输入（自适应多轮）

**目标**：通过充分的交互确认，收集 PRD 每个关键字段所需的真实信息

> **核心原则：交互轮次由信息充分度决定，不设固定上限。** 每轮对话后评估已掌握信息，只有当字段完整性检查清单全部达标时才进入下一步。宁可多问一轮，不要用猜测填充 PRD。

#### 1.1 解析初始输入

1. 检查用户提供的参数：
   - 如果是文件路径，使用 Read 工具读取内容
   - 如果是自然语言描述，直接理解其含义

2. 从用户输入中提取已有信息，标记到字段检查清单中

3. **术语采集（必执行）**：提取用户输入中的业务术语，逐个核实前端实际文案：
   - Grep 只读参考仓库的前端代码（i18n 文案文件、组件 label / placeholder / 枚举文案 / 表头定义），拿到用户可见字面
   - Grep 已有 PRD 目录（1.4 解析出的 `$PRD_ROOT`），看同一对象已有哪些叫法
   - 两边一致 → 直接采用；不一致或多种叫法 → 记下冲突，在 Step 2.1 字段确认卡片列出让用户拍板；都查不到 → 向用户索取界面截图或口述确认

#### 1.2 字段完整性检查清单

以下 10 个字段是生成高质量 PRD 的必要信息。每轮对话后对照此清单评估，决定是否继续追问：

| 序号 | 字段 | 说明 | 充分度标准 |
|------|------|------|-----------|
| ① | **功能名称** | 简洁的中文功能名 | 用户确认过具体名称 |
| ② | **一句话描述** | 功能做什么，给谁用，解决什么问题 | 能清晰回答 What/Who/Why |
| ③ | **核心价值** | 为什么要做这个功能，业务收益是什么 | 有明确的价值主张，非泛泛而谈 |
| ④ | **目标用户** | 主要用户角色和使用场景 | 至少明确 1 个主要用户角色及其典型场景 |
| ⑤ | **需求要点** | 功能包含哪些核心需求项 | 至少有 2-3 条明确的需求点，能区分优先级 |
| ⑥ | **功能边界** | 做什么、不做什么 | 有明确的排除项或边界说明 |
| ⑦ | **页面/UI 涉及** | 是否涉及页面变动，涉及哪些页面 | 明确回答是/否；如是，必须列出具体的页面名称或导航路径（如"用户管理 > 用户列表页"、"首页 > 数据看板"），不可仅回答"涉及前端页面" |
| ⑧ | **验收关键点** | 怎样算功能完成 | 至少 3 条可验证的完成标准（Given/When/Then，有明确预期值） |
| ⑨ | **术语对齐** | PRD 会用到的业务术语在前端界面上的实际文案 | 每个术语都有核实来源（前端代码 / 截图 / 用户确认），且与已有 PRD 叫法不冲突；有冲突时已经用户收口 |
| ⑩ | **异常与边界 / 数据规则** | 空值/超长/无权限/并发等异常场景的预期表现；关键字段的取值范围、必填性、默认值 | 异常场景至少覆盖：输入为空、无权限、数据不存在、依赖服务不可用；核心字段规则完整。AI 先自行起草，用户确认 |

#### 1.3 自适应追问策略

**每轮最多问 2 个问题**（避免用户负担过重），优先追问缺失最关键的字段。

**追问优先级**：② 一句话描述 > ⑤ 需求要点 > ④ 目标用户 > ③ 核心价值 > ⑥ 功能边界 > ⑦ 页面涉及 > ⑨ 术语对齐 > ⑧ 验收关键点 > ⑩ 异常与边界 / 数据规则

> ⑨ 术语对齐优先靠 AI 自己 Grep 前端代码与已有 PRD 解决，**不要把能自己查的东西抛给用户**；仅当查不到、或发现多种叫法需要拍板时才追问（此时可同时索取界面截图）。

**追问方式**：
- 对于封闭性字段（功能名称、页面涉及），使用 AskUserQuestion 结构化选项
- 对于开放性字段（核心价值、需求要点），先展示 AI 的理解/推测，再请用户确认或修正
- **不主动询问技术约束/技术方案**，专注于需求、场景、用户和界面设计

**充分度判定标准**：
- **已确认**：用户明确提供或确认过
- **推测**：AI 从上下文推导，尚未经用户确认
- **缺失**：完全没有信息

**进入下一步的条件**：
- ①②③④⑤ 必须为**已确认**
- ⑥⑦⑧⑩ 至少为**推测**（⑩ 由 AI 先起草异常场景与数据规则，再请用户确认——它是四张表的输入，漏了四表就填不出来）
- ⑨ 术语对齐：每个术语要么已核实（标明来源），要么显式标为「术语未核实（前端文案待确认）」，**不允许静默自造**
- 如果多轮后用户表示"信息就这些了"或"先按这些生成"，尊重用户意愿，将「推测」项标注为 AI 推测并在草稿中高亮提示

#### 1.4 确认落点（先 PRD 根目录，再主题目录）

**PRD 根目录 `$PRD_ROOT` 按以下顺序解析，命中即停，禁止跳级猜测：**

1. **显式参数** —— 用户调用时给出的目录路径。
2. **项目文档** —— 读目标项目的 `CLAUDE.md`、`AGENTS.md`、`README.md` 或贡献指南，看有没有约定 PRD 存放位置与命名规则。
3. **仓库探测** —— 在当前仓库范围内查找既有 PRD 目录：

   ```bash
   export PRD_ROOT=""   # 解析命中后填入；后续所有步骤都用它
   git rev-parse --show-toplevel >/dev/null 2>&1 || echo "不在 git 仓库中，直接跳到第 4 步询问用户"
   find . -type d \( -iname prd -o -iname prds -o -iname requirements \) -not -path './.git/*' 2>/dev/null | head -20
   ```

4. **询问用户** —— 以上都无法唯一确定时，用 AskUserQuestion 让用户给出或确认 `$PRD_ROOT`，**不得默认、不得静默新建目录树**。

**再确认主题目录**：

1. 扫描 `$PRD_ROOT` 下已有主题目录：`ls -1 "$PRD_ROOT" 2>/dev/null`
2. 已有主题目录时用 AskUserQuestion 列出让用户选，**优先引导选择已有主题**，额外提供「新建主题」选项
3. `$PRD_ROOT` 不存在或为空时，**先向用户确认再创建**
4. 主题名沿用该目录既有的命名风格（语言、分词、大小写）；确认后记为 `{主题}`，后续步骤使用
5. **目录简洁原则**：主题按产品大功能划分，不要为每个小功能新建主题

#### 1.5 确认功能名称

   - 从用户描述中提取功能名，使用 AskUserQuestion 确认
   - 功能名使用中文（如"用户注册"、"数据导出"）

> **此步骤在 Step 1 完成后、Step 2 开始前执行**（编号用 1B 而非 1.5，避免与 Step 1 的子节 `1.5 确认功能名称` 混淆）。

  3. **跳过** — 直接进入需求设计

如果选择**跳过**，记录「竞品分析：已跳过」，直接进入 Step 2。

竞品分析完成后，生成汇总洞察并记录，供 Step 2 生成 PRD 时填入竞品分析章节，然后进入 Step 2。

**目标**：在生成 PRD 前，逐字段展示 AI 的理解并请用户确认，然后生成完整 PRD 内容

#### 2.1 字段确认卡片

当信息收集达到充分度标准后，展示字段确认卡片：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
字段确认卡片
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

① 功能名称：{功能名}
② 一句话描述：{描述}
③ 核心价值：{价值}
④ 目标用户：{用户角色 + 场景}
⑤ 需求要点：
   - R-001: {需求1}（P0）
   - R-002: {需求2}（P1）

⑥ 功能边界：

⑦ 页面涉及：{是/否}，{具体页面名称或导航路径列表，如"用户管理 > 用户列表页"}
⑧ 验收关键点：
   - {验收点1}
   - {验收点2}
⑨ 术语对齐（PRD 用词 ← 前端实际文案 / 核实来源）：
   - {术语1} ← 前端显示"{字面文案}"（来源：前端代码 / 截图 / 用户确认 / 未核实）
   - {术语2} ← ...
   冲突：发现的叫法不一致 —— {对象} 在前端叫"X"、已有 PRD 叫"Y" —— 需你拍板统一用哪个

注意：以下字段为 AI 推测（标 * 号），请特别关注：
   *③ 核心价值：{推测内容及推测依据}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

使用 AskUserQuestion 确认：
- 问题："以上字段信息是否准确？"
- 选项：
  1. 全部准确，生成 PRD 草稿（推荐）
  2. 需要修改 — 我来指出哪些字段需要调整
  3. 需要补充 — 还有重要信息没有涵盖

#### 2.2 生成 PRD 草稿

> **技术方案禁令**：生成草稿时，"技术约束"章节必须保持「待补充（由研发人员补充）」，禁止自动填写任何技术方案内容。仅当用户在草稿确认时主动选择「需要补充技术方案」后，才可在下一轮生成技术内容。

> **线框图强制项**：只要需求涉及任何前端页面改动（新增页面、修改现有页面、调整布局、增删界面元素、改变交互），第 5 章「页面 UI/UX 设计」必须包含 ASCII 线框图，改动型需求必须给出「改动前 / 改动后」对照。**禁止仅用文字描述元素位置来代替线框图。**
>
> 判定标准：如果这个需求最终会让用户在界面上看到任何不同，就属于涉及前端页面改动。哪怕改动小到只是"加一个按钮"——越是这类改动，位置与顺序越需要图来确认，文字反而说不清。
>
> 写入文件前自检：涉及前端改动的 PRD，第 5 章有无线框图代码块？没有则补上再写入。

> **术语硬规则**：草稿全文只能使用已核实的前端实际文案，同一对象全文只保留一个叫法。“1.4 术语对照表”必须先完成，再写其他章节，其他章节不得出现对照表之外的新叫法。

基于用户提供的需求信息，直接生成 PRD 草稿并展示关键内容摘要，使用 AskUserQuestion 确认后写入文件。

### Step 3 — 生成 PRD 文件

**目标**：在 `$PRD_ROOT/{主题}/` 下生成完整 PRD 文件

**默认文件名**：`{主题}-{功能名}-{YYYYMMDD}-v1.0-待设计.md`，其中 `{主题}` 必须与所在目录名逐字一致（含大小写与中英文混排）。

**既有约定优先**：1.4 解析出的项目文档、或 `$PRD_ROOT` 下的既有文件若使用了别的命名规则（例如带模块前缀 `mc-`、把状态放在别处、不带日期段），**按既有规则写**，不要用上面的默认式覆盖它。既有文件之间本身不一致时，列出候选让用户拍板。

```bash
# 1. 获取当天日期
date +%Y%m%d

# 2. 确认主题目录名的准确写法，以及既有文件的命名规则
ls -1d "$PRD_ROOT"/*/ 2>/dev/null
ls -1 "$PRD_ROOT"/*/*.md 2>/dev/null | head -20
```

**不使用序号前缀**：PRD 文件名靠「主题 + 功能名」自解释，排序由目录承担——除非项目既有约定另有要求。

**幂等性**：如果目标目录或文件已存在，使用 AskUserQuestion 询问处理方式（覆盖/创建新版本/取消）。

#### PRD 文件格式

**写入文件前必须先读 [references/prd-template.md](references/prd-template.md)，不得凭记忆生成模板结构。**

那份文件包含：frontmatter 字段定义、十章正文模板（概述 / 竞品分析 / 需求与用户故事 / 功能验收清单 / 页面 UI-UX 设计 / 技术约束 / 排除项 / 影响范围 / 非功能要求 / 下一步）、以及逐章填写要求。以下约束容易凭印象写错，必须以模板原文为准：

- 第 2 章（竞品分析）与第 5 章（页面 UI/UX 设计）是**条件章节**，不涉及则整章删除并顺延编号
- 第 6 章（技术约束）**始终保留标题**，内容固定为「待补充（由研发人员补充）」
- 第 7 章（排除项）**不得留空**
- 第 8 章（影响范围）、第 9 章（非功能要求）在完整档为强制项，禁止留空进对外提交
- 本地留存章节需显式标注，便于对外提交时整章剔除

#### 写入文件前术语自检（硬规则，不通过不得写入）

1. 全文每个业务术语都能在 1.4 术语对照表中找到，且写法与「前端实际文案」列一致？
2. 同一对象是否在全文出现了两种以上写法（包括标题、表格、线框图、验收步骤）？
3. 线框图上的菜单名 / 按钮文案 / 列名，是否用的前端真实字面，而非自编的近义词？
4. 是否与 `$PRD_ROOT` 下已有 PRD 的叫法冲突而未经用户收口？
5. 未核实的术语是否已在对照表中标为「未核实」？

任一不达标：先补齐或向用户收口，再写入文件。

#### 写入文件前红线自检（写作红线，不通过不得写入）

0. **档位已判断并明示**：完整档 / 简化档，理由一句话；简化档被省略的章节确属不涉及？
1. 全文无模糊词：尽快 / 友好提示 / 合理 / 大概 / 优化一下 / 体验更好 / 正常情况下？
2. 全文无 TBD / 待定 / 后面再说（豁免项仅限「技术约束-待补充（由研发人员补充）」）？
3. 验收标准：完整档 ≥ 3 条 / 简化档 ≥ 1 条，每条可验证且有明确预期值？
4. 完整档：异常与边界 / 数据规则 / 权限矩阵 / 文案清单四张表无空行，文案为准确文本？
5. 排除项（明确不做）非空？完整档的影响范围、非功能要求已填？

> 本清单与对外提交前的写作红线扫描**同源**。目标项目若另有提测准入检查单，以项目的为准，并在汇报中说明差异。

> **自检与评审的分工**：以上三段写入前自检管**格式合规**（机械可判定，你自己查）；Step 3B 的独立评审管**内容成立性与下游可用性**（需要判断，交子 agent 查）。两者不重复——评审报告里不再查模糊词、验收条数、四表空行这些。

#### 写入文件前项目红线自检（不通过不得写入）

目标项目的 `CLAUDE.md` / `AGENTS.md` / 贡献指南若定义了「凡涉及需求 / PRD / 前端 / 对外文案的产出物必过项」，**逐条给出结论，不得只写"已自检"**。这类清单通常覆盖下面几类，按项目实际写法核对：

1. **合规露出**：PRD 里出现了受合规约束的名称、主体信息、备案信息或对外品牌元素吗？该场景该出现吗？
2. **适用范围**：本需求面向哪个站点 / 租户 / 部署形态？不适用的范围是否已在排除项写明？
3. **开关与默认值**：新增能力有没有配套开关？**默认开还是关，必须在 PRD 里写死**，不得留给研发决定。
4. **存量影响**：方案是否改动既有数据结构或既有模块？若是，必须显式标注冲突风险并给出低侵入替代方案。
5. **硬编码红线**：涉及前端的需求，检查受约束的名称是否被写死在组件、枚举、文案、占位示例里；发现即在 PRD 中标注。

**项目文档没有这类清单时**：跳过本节，并在汇报中写明「项目未定义产出物红线，已跳过」。**不要自行编造一套红线**，也不要把上面的示例当成事实约束写进 PRD。

#### 篇幅提示（不阻断写入）

写入后统计正文行数（不含 frontmatter）。默认阈值如下；`$PRD_ROOT` 下已有足量 PRD 时，改用它们的实测分位数替代默认值。

| 正文行数 | 动作 |
|----------|------|
| ≤ 600 | 不提示 |
| 600 - 900 | 提示一句：「本篇 N 行，长于多数 PRD；研发通常先读需求清单与验收标准」，问是否需要精简 |
| > 900 | 提示并给出**具体可拆分点**——指出需求清单里哪几组彼此独立、能各自成单。**不许笼统说「太长了建议拆分」** |

**长不等于该拆。** 合规改造与用户体系类需求要逐条列举法规要求、要铺权限矩阵，篇幅天然就大。用户说「就这样」就照写，**不要反复劝**。

### Step 3B — 独立评审（完整档必做）

**目标**：用独立视角找出这份 PRD 会被研发、测试打回的理由，以及自己不知不觉加进去的东西。

> **为什么必须交给别人评**：Step 3 那三段写入前自检是你自己执行的，查的是**格式合规**——模糊词、验收条数、四表空行，这些机械可判定，自检查得了。但你知道每个设计决定背后的理由，会把"我当时是这么想的"当成"这样写是对的"。这就是自检永远通过的原因。评审必须交给**拿不到访谈过程**的子 agent，它看到的和研发第一次拿到 PRD 时一样多。

**档位**：完整档必做。简化档（单点 UI / 文案 / 开关配置）跳过评审，但验收标准的覆盖性仍由你自查。

**执行**：读 [references/review-dispatch.md](references/review-dispatch.md)，按其中两份派单模板**并行派发两个子 agent**：

| 评审员 | 只问什么 |
|--------|---------|
| **A — 范围与事实** | 这份 PRD 该不该做这些？说的现状对不对？（MVP 反膨胀 + 架构底座三条件 + 事实底座复核） |
| **B — 可执行性与一致性** | 下游拿这份能干活吗？（研发能开工吗 / 测试能写用例吗 / 线框图与术语自相矛盾吗） |

**派单铁律**：给子 agent 的只有 PRD 文件绝对路径 + 目标项目约束文档路径（`CLAUDE.md` / `AGENTS.md`，项目没有就不给）。**不得转述访谈过程、不得解释设计理由**——一解释，评审就退化成自检。

**结果处理**：合并去重 → 按致命项清单判定 → **可自决项自行修复，只把须拍板项问用户** → 一次性汇报（已修 / 待拍板 / 提示项三段）。七类致命项各自的闭环方式（自行修 vs 问用户）、重跑上限 1 次、禁止二次发问等规则见 `references/review-dispatch.md` 末节。

> **评审不该变成轮询**：评审的价值是找出研发和测试会打回的地方，不是把每个发现都转成一道题让用户答。判断「这项该自己修还是该问」用「决策三级阶梯」：合规必问，行业有通用答案的自己定，产品取舍才问。「需要你拍板」为 0 项时不发起任何提问，直接进 Step 4。

**报告只输出到对话，不落盘**，不生成评审报告文件。

## 注意事项

1. **文件命名规范**：默认 `{主题}-{功能名称}-{YYYYMMDD}-v1.0-{状态}.md`，初始状态固定为 `待设计`，使用 Bash `date +%Y%m%d` 获取日期；`{主题}` 段必须与所在目录名逐字一致。**项目既有命名规则优先于该默认式。****不加序号前缀**，也不得省略主题段——PRD 索引按命名规则校验，不合规的文件会被判为断链。附件类文件例外，形如 `{主题}-附件{X}-{名称}-v{版本}.md`，不带日期与状态段（附件是流程模板，无状态生命周期）
2. **目录位置**：`$PRD_ROOT/{主题}/`（PRD 直接放在主题目录下，不创建功能子目录，保持目录简洁）
3. **内容质量**：PRD 必须包含实质内容，不允许出现 `{占位符}` 或 `TODO`
4. **格式一致**：正文结构以 `references/prd-template.md` 为准。若是在已有占位骨架上细化，按完整模板补齐术语对照表、四张表、影响范围、非功能要求等章节
5. **变更管理**：生成后的 PRD 修改直接编辑文件，并同步 frontmatter 的版本与状态字段
6. **术语一致**：术语以前端实际文案为唯一基准，全文及跨 PRD 保持同一叫法；未核实就标注未核实，不自造、不意译、不静默选边
