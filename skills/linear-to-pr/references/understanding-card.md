# 审阅输出与理解卡模板

配合 `SKILL.md` 的 Step 1.1 与 Step 1.5 使用。判定条件、硬闸门规则以主干为准；本文件只提供输出格式与缺口处理细则。

## Step 1.1 评论/文档审阅输出格式

```text
【TEAM-N 评论/文档审阅】
评论总数：N（已审阅 N）
关键时间线：
- [正文][时间] ...
- [评论 #3][作者][时间] ...
文档/原型/附件：
- [已读取|无法访问] <标题或 URL> — 与需求的关系
冲突与修订：
- 无；或：旧口径 ... ↔ 新口径 ...，当前依据/待确认项 ...
```

填写要求：

- 时间线按 `sequence` 从旧到新，最初描述、关键补充、验收、链接、后续修订和最终结论都要出现。
- 文档/原型/附件逐条标注可访问性。登录墙、私有文档、过期附件写 `[无法访问]` 并计入缺口，不能凭标题猜内容。
- 冲突条目必须写出双方摘要、作者、时间和来源。新评论只有存在明确覆盖证据时才作为候选最终口径。
- 评论中出现但未明确纳入当前 Issue 的新范围，单独列为范围疑问。

## Step 1.5.b 理解卡模板

每项附精确来源：`[正文]`、`[评论 #序号/作者/日期]`、`[文档/URL]`、`[代码 文件:行]` 或 `[推断]`。

```text
【TEAM-N 理解卡】
现象/动机：                     ... [来源]
复现或触发路径：                ... [来源]
期望：                          ... [来源]
验收标准：                      ... [来源]
影响面：                        ... [来源|推断]
真实代码落点/调用链：           ... [代码 文件:行]
最终需求口径：                  ... [采用依据]
```

## 缺口分级处理规则

按 `SKILL.md` Step 1.5 的逐项检查统计缺口数量，然后：

- **0 个缺口**：回显理解卡和实施计划，请用户轻确认。
- **1–2 个缺口**：明确列出缺口清单，并给出带 `[推断]` 标注的假设，让用户补充信息或明确同意按假设推进。
- **≥3 个缺口**，或期望/真实代码落点主要依赖推断：停止，不进入 Step 2 之后的任何写操作。

用户明确同意按假设推进时，把这些假设原样写入 PR body 的「假设」小节（见 `references/git-workflow.md`）。
