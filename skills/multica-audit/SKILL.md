# Multica PR 审计

判断这个 PR 能不能交给人合并。只读：不改代码、不 push、不 approve、不 merge、不在 PR 上发评论。

## 平台约定（Multica）

- **无交互用户。** 只有通过 `multica issue comment add` 发出的评论对人可见；确切命令（含 `--parent`）以运行时指令为准，正文用 `--content-stdin` 加 heredoc 传入。
- 读上下文：`multica issue get <id> --output json`、`multica issue comment list <id> --output json`。
- 取代码：`multica repo checkout <url>`，URL 取自运行时的 Repositories 表。issue 未指明仓库且候选不止一个时，按阻塞处理。
- 只在需要人做决定或补材料时才提醒人（需澄清、阻塞、超出自己权限），常规结果不提醒。写法：`[@名字](mention://member/<user-id>)`，id 取自 issue 的创建人字段与 `multica workspace members --output json`；创建人是智能体或查不到 id 时写纯文本名字。
- **不写任何 `mention://agent/` 链接**，它会重新触发智能体；提到其他智能体只写名字。
- issue 状态按运行时指令处理，本 skill 不额外改状态。
- 一轮只发一条结果评论。结论行是评论的最后一行，写法必须与本文给出的完全一致，其后不得再有任何字符。
- 评论写结论和证据，不写过程；阻塞类评论不超过 8 行。

## 输入

- issue 评论里最近一条 `【PR】<链接>`
- 最近一条以 `【评审结论】可开工` 结尾的规格评论里的验收标准
- `gh pr view <n> --json state,baseRefName,headRefName,title,body`、`gh pr diff <n>`
- checkout 仓库后切到 PR 的 head 分支读完整代码，diff 之外的上下文也要看

## 开审前检查

| 情况 | 处理 |
|---|---|
| 找不到 PR 链接或验收标准 | 不审。原因写在倒数第二行，最后一行 `【审计结论】不通过` |
| PR 已 CLOSED | 同上 |
| PR 已 MERGED | 照常审，报告开头注明「合入后审计，修复需另开 PR」 |

## 审什么

**1. 验收标准。** 每一条都自己验证：读实现，能跑就跑（仓库自己的测试命令，或一条最小命令直接调用被改的函数）。实施评论里的说法不算证据。
对每个被改动的输入，再想一遍规格没写但同类的取值：空值、空白字符的各种形式、0 与负数、超长、Unicode、重复提交。改动让原本正确的行为变错，算 P0。

**2. 目标分支。** PR 的 `baseRefName` 必须是这个仓库的目标分支：

按顺序取证，第一个有结果的就是目标分支 `<base>`：

1. issue 描述或评论显式指定（「目标分支：x」「提到 x」「base: x」）
2. 仓库文档声明的 PR 目标或日常开发基线：`AGENTS.md`、`CLAUDE.md`、`CONTRIBUTING*`、`README*`、PR 模板
3. 远程默认分支：`git symbolic-ref --short refs/remotes/origin/HEAD`

文档与远程默认分支不一致时以文档为准（默认分支常常是发版分支）。三步都没有结果就是无法确定，不要猜。

不一致记 P0。无法确定仓库的目标分支时记「无法验证」。

**3. 规格外改动。** diff 里不属于任何验收标准的改动逐条列出（版本号、依赖、格式化、顺手重构）。会改变行为或发布内容的记 P1，其余记 P2。

**4. 安全。** 密钥或内网地址进了 diff；外部输入未校验；权限或租户过滤被放宽；新路由没挂鉴权。

**5. 测试。** 每条验收标准是否有会因实现错误而失败的测试；没有的记 P1。

## 分级与结论

| 级别 | 含义 |
|---|---|
| P0 | 验收标准不成立、行为回退、目标分支错误、安全问题 |
| P1 | 该修但不至于出错：缺测试、会影响发布的规格外改动 |
| P2 | 提示，不要求修 |

| 结论 | 条件 |
|---|---|
| `【审计结论】通过（评级 A）` | 标准全部通过，无 P0、P1 |
| `【审计结论】通过（评级 B）` | 标准全部通过，无 P0，有 P1 |
| `【审计结论】不通过` | 有 P0，或有标准「无法验证」 |

最后一行只能是这三种写法之一，不加冒号、原因或其他后缀；原因写在正文里。

## 评论格式

```markdown
## 审计报告

PR：<链接>（`<head>` → `<base>`）

### 验收标准
| # | 标准 | 判定 | 证据 |
|---|---|---|---|
| 1 | | 通过 / 不通过 / 无法验证 | `文件:行` 或命令与输出 |

### 发现
| 级别 | 位置 | 问题 |
|---|---|---|

### 规格外改动
没有就写「无」。

### 必须修复
1. `文件:行`：问题 → 怎么改
通过时写「无」。

【审计结论】不通过
```

## 规则

- 「无法验证」不等于通过，写明缺什么证据。
- 只报影响正确性、需求符合度、安全的问题，不报风格偏好。
- 「必须修复」要具体到研发能直接在原 PR 上追加提交。
- 复审时只看上一轮的必须修复项和它们可能带来的回归，标题写 `## 审计报告（第 N 轮）`。
